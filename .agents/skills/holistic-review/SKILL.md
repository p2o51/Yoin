# 整体审阅

## 1. 先弄清楚审什么

- 范围：整个项目、一个功能、一个页面，还是一次改动（分支或 PR）。
- 给谁用，在什么场景下用；现在处于哪个阶段（探索、打磨、上线前）。
- 用户没说的，先从 README、`docs/`、最近的提交和 Notion（如通过 Notion MCP 搜索「公文包」或对应项目页面）里找。还不清楚，就问一句。

## 2. 收集证据

- 读项目结构、README、`docs/design.md`、`docs/platforms.md` 等设计文档，以及相关页面的布局和文案文件（Android 与鸿蒙看 `origin/main`，iOS / macOS 与 `:shared` 注意检查对应的开发分支或合入基线）。
- 能运行的、有截图的、有 Figma 链接的，都去看实际界面。看不到界面时，在报告里写明只审了代码和文档。
- 审一次改动时，先用 `git diff <base>...HEAD --stat` 看改到了哪些地方，再挑出和用户体验、跨端对齐、文档/Tips 同步有关的文件细读。

## 3. 逐项检查

1. **目标**：这个功能帮用户解决什么问题？流程里有没有多余的步骤，有没有漏掉的步骤？
2. **一致性**：同类元素的样式、间距、动效、命名、交互是不是一致？是否符合项目已有的设计语言？
3. **四端对齐（Android / iOS / 鸿蒙 / macOS）**：核心交互逻辑、状态流转、能力门控（`Capability`）、自适应窗口档位与术语是否四端一致？若因平台能力或进度限制只在单端先行，是否在 `docs/platforms.md` 中明确记录了跨端缺口与原因？
4. **信息结构**：层级、导航、默认状态、空状态、加载状态、错误状态是否齐全？
5. **文案**：术语是否统一（参照 `docs/i18n/zh-glossary.md` 与 `01-yoin-facts-and-terms.md`），语气是否一致，有没有 AI 腔或违规隐私承诺，错误提示有没有告诉用户下一步怎么办。
6. **可访问性**：对比度、触控区域、字号、读屏标签。要细查时用 `accessibility-review`。
7. **文档与 Tips 同步**：用户可见功能、音源行为、设置项、快捷键或能力限制的改动，是否同步更新了对应的 `docs/` 规范（及 `harmony/docs/`、`iosApp/docs/`）；新增或调整手势、快捷键、隐藏入口时，是否同步更新了应用内 Tips（`HomeBubbleTip` / `ui/tips/` 等，且文案经 Argon 生成）；若为发版审阅，是否已按 `release-docs-sync` 完成 `README*`、事实文档与 `yoin-site` 同步检查。
8. **跨模块**：不同页面或模块之间有没有冲突、重复实现、行为不一致。
9. **风险**：上线后用户最可能碰到的问题是什么。

## 4. 输出格式

```markdown
## 整体审阅：<审阅对象>

**范围**：…
**依据**：看了哪些分支、文件和界面，哪些没看到

### 结论
一两句话：最大的问题是什么，最值得保留的是什么。

### 四端对齐与文档 / Tips 同步
| 检查项 | 状态 | 说明（含缺口 / 待同步文件） |
| --- | --- | --- |
| 四端对齐（Android / iOS / 鸿蒙 / macOS） | | |
| 仓库文档与平台矩阵（`docs/`） | | |
| 应用内 Tips 同步 | | |

### 问题清单
| # | 严重度 | 位置 | 问题 | 建议 |
|---|--------|------|------|------|

严重度：🔴 必须改 / 🟡 应该改 / 🟢 可以更好

### 文案修改建议
| 位置 | 原文 | 建议 | 理由 |
|------|------|------|------|

### 交给 Claude 的改动
- [ ] <分支:文件或模块>：<现象> → <建议的改法>

### 做得好的地方
```

## 规则

- 每个问题都要有证据：文件路径、行号或截图里的位置。不写“体验可以更好”这种空话。
- 只报真实存在的问题，按严重度排序。某一项没发现问题就写“未发现问题”，不要凑数。
- 不改代码。文案要改的话，按 `copy-rewrite` / `write-copy` 的流程来。
