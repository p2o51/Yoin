# 写文案

Yoin 的文案应该兼具清晰的界面画面、准确的工程细节与诚实的创作者视角：既不写成堆砌辞藻的广告词，也不写成没有温度的技术文档。

撰写或修改文案前，请先阅读以下两个参考文档：

- [01｜Yoin 事实与术语](./references/01-yoin-facts-and-terms.md)
- [02｜Yoin 语气与例句](./references/02-yoin-tone-and-examples.md)

## 1. 整体语感与用词规范

- **官网、商店页与更新说明**：简洁、克制、自信。可以由界面组件做主语，也可以直接称呼读者为“你”；保留适度的西式直译冷感与极客幽默（如“我们克制地为你提供了这些音乐工具，希望你不要讨厌”）。
- **开发手记**：采用第一人称（我 / 我们）叙事，记录真实的设计考量、工程取舍与测试结论。行文应当是**干净、平实的现代书面语**，切勿将“第一人称叙事”误解为北方俚语、评书腔或自媒体评测体。
- **常用词汇与禁用词**：
  - **推荐使用**：`整理、准备、对比、核对、适配、记录、由于、因此、同时、此外、相比之下、仅凭`。
  - **避免使用**：`随手试、拿不准、拉了一份、站得住脚、干脆、啃骨头、埋雷、照妖镜、咬得很紧、巧妇难为无米之炊、翻盘、这笔账很容易算、吃零分、老不老实、瞎猜、瞎编` 等口语套话。
  - **视角表述**：作者常住海外，涉及中国大陆网络无需代理直连时，统一表述为“**中国直连**”，不写“国内直连”或“国内网络”。

## 2. 结构与信息分层（避免过度说明书化）

每个模块的文案需明确三个层次，**切忌在官网、更新日志或手记里把所有操作步骤、参数选项、边界条件写得过细**：

1. **使用场景**：用户在什么情境下使用这项功能（例如记录对当前配乐、歌词、编曲的感受或应援词）。
2. **界面与技术支点**：只点出核心的交互动作或技术亮点（例如笔记锚定在进度条对应的秒数、基于 Material 3 Expressive 的弹簧动画、跨窗口像素级对齐的导航栏）。
3. **把具体规则留给使用文档**：
   - **留在正文/更新日志的**：这项功能能做什么、带来了什么核心变化（一句话讲清即可，如“自定义服务支持接入 OpenAI 与 Anthropic 兼容接口，并可自由搭配外接搜索服务”）。
   - **下沉到使用文档 / 设置页内提示的**：具体的表单字段列表、有哪些下拉选项（如“不思考、低、中、高”“原始、320、192、128 kbps”）、按钮长什么样、未登录读哪个域名、失败了怎么回退、每次最多查几首歌、快捷键的完整键位表等。**不要把更新日志或功能介绍写成逐个控件的操作说明书。**

## 3. 标题写法

- **官网模块标题**：
  - 默认使用简短的名词短语或动宾短句加句号（如 `为听过的音乐留下痕迹。`、`让所有音乐存放在一处。`、`从掌心到大屏，处处合手。`），省略“让你能够…”“为你提供…”等前缀。
  - 每页可安排 1–2 处轻巧的双关、拟人或音乐彩蛋（如 `音犹未尽？`、`用过 Spotoolfy？`、`小小女孩与大大屏幕`）。
- **开发手记标题与小标题**：
  - 避免使用汇报体或自媒体式标题（如“先拿 35 首歌筛一轮”“九组方案跑满全量”“新歌不联网，只剩 8.9%”“算一笔速度与开销的账”）。
  - 使用偏正名词短语、空间/音乐意象或双关歌名（如《从不离开的导航栏》中的 `三个按钮的宽度守恒`、`曲目切入的方向感`、`隐形的基准线`；《关于 499 首歌的“关于”测试》中的 `摘要之外与正文深处`、`检索的边界与模型的克制`、`记忆止步的年份`、`语种温差与隐秘角落`、`当模型面对空白`、`Need for Speed`）。
- **中英文独立撰写**：英文标题采用自然的日常短语或对称句式，不从中文逐字硬译；提供英文文案时附简短的语感说明。

## 4. 正文与更新日志写法

- **具体交互先行，点到为止**：先描述界面变化与核心体验，不罗列琐碎的参数档位、错误码、像素/倍数或后台逻辑。
- **更新日志（Changelog）的精简原则**：
  - 每一条只写**用户感知最明显的核心变化**（控制在 1–2 句话），删掉“点什么按钮弹出什么菜单、有哪些枚举项、失败了怎么恢复、未登录读什么默认地址”等说明书式的细节。
  - 细碎的 UI 微调合并概括，不再逐个页面点名（如不说“列表顶部的潮线扩展至 A、B、C、D、E、F、G 页面”，直接写“将列表顶部的‘潮线’渐隐边缘扩展至更多面板与设置页”）。
  - **随日志输出文档同步提示**：撰写发布说明或更新日志时，凡是按上述原则从日志里精简下沉掉的具体规则、选项、额度限制、平台差异或数据/SDK 变动，**必须**在更新日志之外另附一段简明的 **「文档同步提示（Doc-Sync Note）」**，列出需要同步补充到仓库 `docs/`（如 `docs/design.md`、`docs/platforms.md`、`01-yoin-facts-and-terms.md`）与官网 `yoin-site`（`public/docs.html`、`public/zh/docs.html`，若涉及数据流向/SDK/AI 或密钥存储则加列 `public/privacy.html`）的具体条目（完整同步步骤见 [release-docs-sync](../release-docs-sync/SKILL.md)）。
- **数据与评测手记的取舍**：当页面已有图表展示明细数据时，正文不要逐项罗列数字，也不要插入生硬的汇率或时间注释。正文应聚焦于测试方法、关键规律与工程取舍，并在 3–4 处自然呼应小标题的意象（避免每段刻意点题）。
- **需要避免的五类问题**：
  1. **说明书式罗列参数与操作步骤**：把原本属于使用文档或界面内提示的枚举项、配置流程、快捷键清单全塞进正文或更新日志。
  2. **暴露代码兜底与防御性免责**：在功能介绍中解释异常分支或退路（如“查不到的就空着”“若服务拒绝则恢复原位并提示”）。
  3. **口语套话与自媒体腔**：见第 1 节禁用词列表。
  4. **空洞修辞**：使用脱离具体功能的抽象比喻或公关套话。
  5. **超出事实边界的承诺**：涉及隐私、联网与数据存储的表述，须与隐私政策及 [01｜Yoin 事实与术语](./references/01-yoin-facts-and-terms.md) 保持一致。

## 5. 审改与输出规范

- **审改作者原稿**：仅修改事实与术语出入、防御性免责表述、过度琐碎的说明书细节，以及明显的错别字或语病。作者表达设计考量、创作者自豪感、西式直译语感及图注冷幽默的句子（见 [02｜Yoin 语气与例句](./references/02-yoin-tone-and-examples.md)），均保持原貌。
- **重写或优化 AI 初稿**：去除口语套话、汇报式标题、账本式报数与说明书式的冗长参数罗列，对齐 Notion 文案库的区块格式（`- [ ] <b>区块</b><br /><b>位置</b>　文案`）。
- **输出方式**：审改时按页面顺序输出对比表格（`位置｜现行文案｜原因｜建议改法`）；未经确认，不直接覆盖原稿页面。撰写发布说明或更新日志时，成稿后另起 `### 文档同步提示` 列出对应 `docs/` 与 `yoin-site`（`public/docs.html` / `public/zh/docs.html` 等）需补齐的规则与选项（若 `agy -p` 仅要求纯商店文案文本则置末或标明供文档同步使用）。
