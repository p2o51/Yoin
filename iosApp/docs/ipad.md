# iPad / 大屏

## 结论

**推荐方案 A「顶栏 + 同窗分列 + 右侧检查器」**：导航交给 iPadOS 26 的顶部玻璃 Tab 栏（可变侧边栏），正在播放变成底部浮动的玻璃小胶囊，详情页在宽窗口里作为同一窗口的右列打开，Now Playing 的「侧栏」用系统的 Inspector（右侧检查器）来做。
Android 的八条适配原则全部保留，只把「一条栏」拆成 iPad 习惯的「上面导航、下面播放」。

## 先说 iPadOS 26 的几个新规矩（给 Android 背景）

| iPadOS 26 | 相当于 Android 的 |
| --- | --- |
| 窗口可以随意拖成任何大小（新窗口系统 / 台前调度），左上角有红黄绿三个窗口按钮 | 自由窗口 / 桌面模式，而且是默认行为 |
| `TabView` + `.sidebarAdaptable`：Tab 栏浮在**顶部中间**，是一块玻璃；用户可以把它展开成左侧侧边栏 | 没有直接对应；像 Navigation Rail 能展开成 Drawer，但位置在顶部 |
| `.tabViewBottomAccessory`：Tab 栏旁边的一条「附件」，音乐 App 用它放迷你播放器。iPad 顶栏模式下它浮在内容底部 | Yoin 底栏里的正在播放 pill |
| `NavigationSplitView`：系统的两栏 / 三栏 | `ListDetailPaneScaffold` |
| `.inspector`：从右边推出的一列，宽窗口里和内容并排，窄窗口里自动变成底部弹层 | 侧边 sheet，正好对应 Yoin 的 NP Panel |
| 顶部的菜单栏（鼠标移到顶上或下滑出现） | 无；需要我们提供「播放」菜单和快捷键 |

## 先守住的 Android 原则（不变）

1. **只看自己的容器，先判高再判宽。** 不用系统的 `horizontalSizeClass`（它只有 compact / regular 两档，太粗），读容器的实际宽高，照搬 600 / 840 两条线和「高 < 480 先出局」。iPad 窗口能拖成任意大小，所以这一条在 iPad 上比在 Android 上更重要。
2. **一个窗口一棵树、一套 Now Playing 状态链：Closed → Panel → Full。**
3. **详情是同一窗口里的列，不是第二个窗口。**
4. **换档不落在弹簧中途；数量跟宽度走，卡片内部不缩放。**

## 方案 A（推荐）：顶栏 + 同窗分列 + 检查器

```
iPad 横屏 1180 × 820，开着一张专辑和 NP 侧栏
┌──────────────────────────────────────────────────────────────────┐
│ ● ● ●            ╭─────────────────────────╮                      │  ← 窗口按钮
│                  │  Home   Library   ⌕     │  玻璃 Tab 栏（顶部）  │
│                  ╰─────────────────────────╯                      │
│ ┌────────────── shell 列 ─────┐ ┃ ┌── 详情列 ─────┐ ┌─ NP 检查器 ─┐ │
│ │ Home feed                   │ ┃ │ ▣ 专辑封面     │ │   ▣ 封面    │ │
│ │ ▣ ▣ ▣ ▣                     │ ┃ │ 标题 / 评分    │ │   歌名      │ │
│ │ ▣ ▣ ▣ ▣                     │ ┃ │ 1. 曲目        │ │ ~~~~~──     │ │  ← 波浪进度条
│ │ Recently added …            │ ┃ │ 2. 曲目        │ │ ◁◁  ▶  ▷▷  │ │
│ └─────────────────────────────┘ ┃ └───────────────┘ └─────────────┘ │
│             把手（可拖，只钳制）┛                                    │
└──────────────────────────────────────────────────────────────────┘
NP 侧栏关着时，底部浮一颗玻璃胶囊： ╭ ▣ 歌名 · 歌手  ~~~── ▶ ╮
```

**导航：** `TabView` 用 `.sidebarAdaptable`，Tab 是 Home、Library、搜索（`role: .search`）。Library 的筛选（专辑 / 歌手 / 歌单 / 歌曲）做成 `TabSection`：顶栏里它们收在 Library 一个 Tab 里，用户展开成侧边栏时它们变成侧边栏条目，iPad 用户会觉得很自然。窄窗口（< 600）或 iPhone 上同一套代码自动变回底部 Tab 栏。

**正在播放的三档：**

- **Closed**：迷你播放器用 `.tabViewBottomAccessory` 放，浮在内容底部中间，是一颗带封面色的玻璃胶囊，里面有小号波浪进度条。点它进 Panel 或 Full。
- **Panel**：用 `.inspector`，宽 = clamp(窗宽 × 0.5, 360, 420)，和 Android 的侧栏同一个公式。旁边的内容让位、继续可用。可用条件照搬：高 ≥ 480 且旁边还剩 ≥ 320；开着详情列时要剩两列 + 槽 = 744。
  注意：系统的 Inspector 在窄窗口会自己变成底部弹层，这和 Yoin 的规则（不可用就直接 Full）不一样，所以要我们自己判断：不够宽就不弹 Inspector，直接进 Full。
- **Full**：整窗播放器，从迷你胶囊用 zoom 转场放大（iOS 18 起的 `.navigationTransition(.zoom)`，相当于共享元素转场）。宽窗口是双栏：左封面、右歌词。

**详情列：** 宽 ≥ 840、高 ≥ 480 时，专辑 / 歌手 / 歌单在当前 Tab 里作为右列打开，列宽公式照搬 `resolvePaneBudget`（shell 份额 0.45，≥ 1080 时 shell ≥ 600，两列都 ≥ 360），中间是我们自己的拖动把手。这里**不用 `NavigationSplitView`**：它的左栏是给「列表」用的（会被系统画成侧边栏材质、带收起按钮），而 Yoin 的左列是一整个 Home feed。自己用一个两列布局，和 Android 的 `PaneSplit` 同一个思路。窄于 840 时，详情用普通的推入（`NavigationStack`），封面带 zoom 转场。

**iPad 专属的补充：**

- 菜单栏加一个「播放」菜单：播放 / 暂停（空格）、上一首 / 下一首（⌘← / ⌘→）、喜欢（⌘L）、打开正在播放（⌘P）。不提供的话 iPad 用户按键盘会没反应。
- 鼠标悬停：卡片用 `.hoverEffect(.lift)`。
- 多窗口：每个窗口一棵树、各自的 Panel / Full 状态；播放器只有一个，所有窗口共享。可以支持「把专辑拖出去成新窗口」，但不是第一期。
- 窗口拖动缩放时是手指驱动，跟 Android 拖把手一样按实时宽度换档；卡片位置弹簧在拖动时关掉，1:1 跟随。

**代价：** Android 上「Home | 正在播放 | Library」是一整条栏，iPad 上拆成了上下两块。我认为值得：顶栏是 iPadOS 26 所有 App 的共同位置，用户的手和眼睛已经习惯去那里找导航；播放胶囊留在底部，仍然是 Yoin 那颗带封面色的胶囊。

## 方案 B：保留 Yoin 自己的底栏

```
┌──────────────────────────────────────────────┐
│ ● ● ●                                        │
│  Home feed / 详情列（同 A）                   │
│                                              │
│      ╭──────────────────────────────────╮    │
│      │ Home │ ▣ 歌名 · 歌手 ~~~ │ Library │    │  ← 自绘玻璃 Button Group，居中限宽 600/720
│      ╰──────────────────────────────────╯    │
└──────────────────────────────────────────────┘
```

隐藏系统 Tab 栏，在底部居中画 Yoin 自己的玻璃 Button Group（导航 / 详情 / 合体三种姿态，和 Android 逐一对应）。

- 好处：品牌最统一，iPhone、iPad、Android 是同一条栏；Android 的栏几何纯函数（`resolveBarGeometry`）可以原样翻译。
- 坏处：没有可展开的侧边栏；键盘和辅助功能的焦点顺序、窗口按钮避让、菜单栏都要自己补；和 iPadOS 26 所有其他 App 的位置不一样，第一次用会找不到。
- 适合：如果 51 认为「一条栏」是 Yoin 的核心身份，比 iPad 习惯更重要。

## 方案 C：侧边栏 + 常驻播放列（像 Mac 上的音乐 App）

```
┌────────────┬──────────────────────────┬──────────────┐
│ ● ● ●      │                          │  ▣ 封面       │
│ Home       │  专辑网格 / 详情          │  歌名         │
│ Library    │                          │  ~~~~──       │
│  · 专辑    │                          │  ◁◁  ▶  ▷▷   │
│  · 歌手    │                          │  歌词 …       │
│  · 歌单    │                          │              │
│ Memories   │                          │              │
└────────────┴──────────────────────────┴──────────────┘
```

`NavigationSplitView` 三栏：左侧边栏、中间内容、右边常驻正在播放（≥ 1180 才常驻，否则收成 A 的检查器）。

- 好处：接键盘、横屏时信息密度最高，最像桌面音乐软件。
- 坏处：和 Android 的模型差最远：Library 的筛选胶囊变成侧边栏条目，Home 的 feed 被挤到中间，Now Playing 失去「Closed → Panel → Full」这条链的前两档；而且 Yoin 的「列里不要第二个窗口感」会被三栏边框打破。
- 适合：以后如果做 Mac 版（Catalyst 或原生），这个方案可以直接拿过去。

## 建议的下一步

1. 先按方案 A 搭骨架：`TabView(.sidebarAdaptable)` + 底部附件胶囊 + 自绘两列布局 + Inspector。
2. 把 Android 的三个纯函数原样翻成 Swift（最好放进 KMP 共享层，连单测一起共享）：窗口档位（`rememberYoinWindowInfo` / `forPaneWidth`）、列宽（`resolvePaneBudget`）、NP 档位（`NowPlayingPresentation`）。这样 iPad 和 Android 在同样的宽高下一定给出同样的答案。
3. 在 Mac 上用 iPad 模拟器把窗口从 1366 一路拖到 400 宽，对照 `adaptive-principles.md` 末尾的「各窗口一览」表逐行检查。
