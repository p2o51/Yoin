## 怎么读这份清单

- **范围**：这次把 7 个方向审计里确认过的问题全部合并了。同一个原因在几个地方都出现的，算一条，各处症状都写在这条下面。合并后一共 **74 条**：P0 有 4 条，P1 有 20 条，P2 有 50 条。
- **行号**：以分支最新提交 091ffe91 为准。审计期间分支已经从 3dd4c82c 往前走到了 eec6dca4 和 091ffe91。
- **文件简写**（都在 `iosApp/Yoin/` 下）：
  - SAO = Playback/SpotifyAudioOutput.swift
  - SR = Playback/SpotifyRemote.swift
  - PE = Playback/PlayerEngine.swift
  - 安卓路径都在 `app/src/main/java/com/gpo/yoin/` 下。
- **"停泊"是什么意思**：Spotify 在放一首 Yoin 不认识的歌，Yoin 就把它当成"Spotify 自己的歌"来显示，自己的队列停在原地不再往前走。

**三个根本原因**（大部分问题都出自这里）：

1. **本机只交给 Spotify 一首"下一首"**。这个做法本身导致了大量停泊、残留歌、改了队列不生效、锁屏后状态错乱。
2. **App Remote 断掉或"连着但不干活"时，没有统一的兜底**。界面会骗人、卡死，命令会丢。
3. **陪伴模式下，Spotify 自己的歌只是"显示"出来**。不记历史，爱心不刷新，按钮作用到 Yoin 隐藏的队列上。

**最近两个提交的问题**：

- **3dd4c82c**：#5 和 #6 修得不完整；#13 是它带进来的回归；#37 的新列表本身也有毛病。
- **eec6dca4**：#1 是它带进来的回归；#8 修得不完整；#30 有把本机踢下 Connect 的风险。

## P0（4 条）

**#1 [P0] Spotify 拒绝被唤醒时，Yoin 把整个队列一首一首跳完（eec6dca4 的回归）**
- **用户会遇到**：测试者那种"App Remote 每次都连不上"的手机上，点一首歌，约 1.5 秒后提示"Spotify didn't accept Yoin…"，然后跳到下一首，再失败，再跳。每跳一首弹一次"已跳过"，最后整个队列标成失败。Spotify 原来的歌照常放。如果 Spotify 是带着错误跳回来的（比如用户在 Spotify 里拒绝授权），那么每跳一首都会切到 Spotify 一次。歌放完自动换下一首时也会这样。
- **原因**：eec6dca4 把"已安装但打不开"的提示改成了 handOffRefused。但出错处理只把"没装 App"和"需要会员"当作"停在当前歌"，其他情况（包括 handOffRefused、带错误的跳回、缺 Client ID）都被当成网络错误，于是跳下一首（SR:241-248、277-279；SAO:158-164、619-622 → PE:591-616、729-733）。
- **安卓怎么做**：所有连接失败都分了类型，停在当前歌并给提示，从不因为连接失败跳歌（SpotifyAppRemotePlayer.kt handleRemoteError/publishError）。用户每点一次，最多替他打开一次 Spotify（reportUnreachable）。
- **修法**：出错回调一律"停在当前歌"：清掉 starting/awaitingWake/wakeWait，设 failedHere 和 quietPause，再按网络错误报出（outputDidFail(network:true)）。handOffRefused 和缺 Client ID 时显示"去设置"按钮。同一次加载被拒后不再唤醒。回调按发起时的 generation 过滤掉过期的。
- **需要真机**：不需要，代码确定。修完后用真机回归一次。

**#2 [P0] 唤醒 Spotify 之后连不上：卡在 0:00，播放、暂停、拖动、点歌词全部没反应**
- **用户会遇到**：Yoin 打开 Spotify 去开播。Spotify 放了歌并跳回来，或者用户卡在 Spotify 的登录/授权/错误页面上，自己手动回来。如果这时 App Remote 连不上，Yoin 一直停在 0:00，而 Spotify 那边在放。所有按钮都没反应，也不会换歌，只有点另一首歌才能脱身。
- **原因**：awaitingWake 和 starting 这两个"正在开播"的标记只有连接成功才会清掉。跳回来时只连一次，没有重试，也没有超时（SR:252-281、357-363）。回到前台虽然开了轮询，但应用状态的地方和 watch 都被"正在开播"挡住（SAO:1689、1447、1451），播放和暂停也被挡住（1242、1270），拖动只改本地时钟（1285）。出错回调清了 starting，却留下了 awaitingWake。
- **安卓怎么做**：主线的 reportUnreachable/settleHeldStart 不会让开播卡在没有出口的状态。PR #243（还没合并）给唤醒 8 秒宽限期，期间重试连接。
- **修法**：从唤醒打开 Spotify 那一刻开始计时，大约 8 秒。期间每次回到前台都带退避重试连接。时间到了用 me/player 确认：歌已经在本机放了，就按"开播成功"处理；否则停住，提示"打开 Spotify"。所有结束路径（包括出错回调、既没 token 也没错误的跳回）都要清掉 awaitingWake 和 wakeWait。
- **需要真机**：不需要。

**#3 [P0] 改过随机/循环/队列后再按播放：Yoin 对本机发 Web API 开播，把 iPhone 上的 Spotify 踢下 Connect**
- **用户会遇到**：在本机用 Yoin 放专辑，中间切一下随机或循环，或者用"下一首播放"、拖动排序、删掉下一首（暂停时做也一样）。暂停之后再按播放，Yoin 不是接着放，而是对本机发 PUT me/player/play。这正是文档里记录的会把本机 Spotify 踢下 Connect 的请求：Spotify 停掉或不理，之后 Web API 返回 404，Yoin 显示"无法播放"或卡住。
- **原因**：play() 里"重新交接下一首"的判断没有排除本机（SAO:1237-1250）。任何队列或模式改动都会让"已交给 Spotify 的那首"和"引擎认为的下一首"对不上（703-707、1127、1145），于是走到 send()，对本机 id 或 nil（即当前设备，也就是本机）开播（893-917）。另外 apply(now) 会把目标设备写成本机 id（1715）。
- **安卓怎么做**：从不靠重新开播来换下一首。随机和循环走 App Remote 的 setShuffle/setRepeat（PlaybackManager.kt:736-759）。
- **修法**：play() 的重新交接条件加上"不是本机"，本机一律用 App Remote 继续播放。apply(now) 在识别出本机（且不是 Mac）时保持目标为空，跟 followTransfer:873、watch:1474 的做法一致。已交接但过期的那首歌，在歌曲边界处理（见 #4、#10）。
- **需要真机**：不需要。会把本机踢下线已有 11-06 的日志为证。

**#4 [P0] Yoin 塞进 Spotify 队列的"下一首"会一直残留：重复放、顺序乱、污染用户自己的 Spotify 队列**
- **用户会遇到**：本机放专辑，A 在放，Yoin 已经把 B 放进了 Spotify 队列。
  - (a) 在 Yoin 按下一首：B 放完又放一遍 B，然后才是 C。
  - (b) 按上一首，或在队列里点更后面的歌：那首放完冒出旧的 B，Yoin 把它当成"Spotify 自己的歌"，不再跟自己的队列走。
  - (c) 换放另一张专辑：第一首之后插进上一张专辑的 B。
  - (d) 停止，或换去放服务器/Apple Music 的歌：B 留在用户的 Spotify 队列里，下次用户在 Spotify 里听歌时冒出来。
  - (e) Yoin 开播后，用户转去 Spotify 放自己的歌单：第一首之后插播 Yoin 留下的那首。
- **原因**：enqueueNext 把下一首写进 Spotify 会长期保留的用户队列（SAO:703-729）。而 Yoin 每次换歌都是 load() 再 remote.play(uri)（190-236、462-473），只换当前这首，不清队列。load() 和 stop() 直接把"已交接的歌"记录清空（198、1592-1624），忘了 B 还在队列里。下一首正好是已排进队列的那首时，也从不用"跳到下一首"。
- **安卓怎么做**：上一首/下一首调用 Spotify 自己的 skipNext/skipPrevious（PlaybackManager.kt:707、718）。开播从不往用户队列追加（SpotifyAppRemotePlayer.kt:329）。SpotifyStartPlan.kt:12-18 记着 51 在 2026-10-05 抱怨的正是这个问题。
- **修法**：
  - 按先进先出记下"已塞进 Spotify 但还没放"的歌。
  - 下一首正好是队首时，用 remote.skip(forward:) 而不是 play(uri)。
  - Spotify 放到已知的残留歌、而它不是引擎当前的歌时，跳过它，不标成外部歌。用 GET me/player/queue 核对。
  - 更好的做法是只在需要时才塞：进后台时（在 beginBackgroundTask 保护下），或在前台的最后约 15 秒。这样残留很少，中途改队列也不用纠正。
  - (e) 属于平台限制，写进 spotify-background.md 和 qa-script.md。
- **需要真机**：Spotify 队列的具体行为要真机确认；代码逻辑是确定的。

## P1（20 条）

**#5 [P1] App Remote"连着但不干活"时，暂停/播放/上下首会丢；丢掉的暂停还会被自动撤销；点歌词在重连失败时也会丢（3dd4c82c 修得不完整）**
- **用户会遇到**：测试者遇到的"连着但不干活"再次出现时：
  - 按暂停，按钮显示已暂停，音乐却继续放；最多 10 秒后 Yoin 自己又变回"播放中"。
  - 按下一首没反应，也没有任何机制发现它丢了。
  - 点歌词，歌词跳过去了，音乐没动。重连失败的话（测试者手机上连接常常 10 毫秒就失败），之后就再也没有动作，要等 10 秒后的 watch 才把歌词拉回去。
- **原因**：
  - 暂停/继续/切歌不带完成回调（SR:327-333）。command() 只要连接显示"已连接且没坏"就直接发出去（SAO:1324-1328）。
  - 只有拖动有"回声检查"，即检查 Spotify 有没有真的照做（awaitSeekEcho，1304-1318）。它重连失败就直接放弃，没有改走 Web API（对比 command() 1338 行有）。
  - "连着不干活"的检测只在 me/player 和界面不一致时触发（1506-1527）。切歌丢了两边还是同一首，永远发现不了。
  - 暂停丢了会触发换连接，而新连接的第一个状态走外部分支，把"想要播放"设回 true（1852-1856），于是界面翻回播放。
  - 换连接 60 秒内最多一次。
- **安卓怎么做**：命令都经过 enqueueOperation，失败交给 handleRemoteError 重连；断开时命令留着，重连后执行（SpotifyAppRemotePlayer.kt:461-491、758-790）。安卓也不检测"连着不干活"，但不会把界面翻回去。
- **修法**：
  - 暂停/继续/切歌也加回声检查：2.5 秒内应该看到暂停状态对得上；切歌应该看到 uri 变了。否则标记连接已坏、重连、重发一次，重连失败就改走 Web API。
  - 只重发用户几秒内发出、还没被确认的操作，不覆盖用户之后在 Spotify 里做的改动。
  - 有命令在等确认时，不受 60 秒间隔限制。
  - 拖动的回声检查重连失败时，也改走 Web API 拖动；再不行就读一次 me/player，把时钟拉回真实位置。重连成功后的那次重新拖动，也再检查一次。
- **需要真机**：不需要。

**#6 [P1] 检测"连着不干活"的补丁（3dd4c82c/091ffe91）不完整：60 秒只换一次，已坏的连接挡住所有兜底，换连接失败也不轮询，还会误判**
- **用户会遇到**：
  - "连着不干活"再次发生（51 的 11-08 日志里，换上的新连接又出了同样的问题），或者离上次换连接不到 60 秒（短歌，或上一首误判过）：歌放完时 Yoin 停在 -0:00、进度条满格，最长一分钟；点歌词只改 Yoin 的显示。
  - 换的新连接也连不上时，只能每 10 秒跟一次。
  - 锁屏几分钟再回来，一个好好的新连接也可能被误判拆掉，正确的歌晚 1–2 秒才出现，还占掉之后 60 秒的换连接机会。
- **原因**：
  - checkRemoteSilent 在 60 秒内什么都不做，而且从不应用 me/player（SAO:1506-1521）。歌曲结尾的超时检查每首只做一次（1926-1930）。
  - refresh、becameActive、watch 的兜底都按"已连接"判断，而不是按"已坏"判断（1595、1577、1457）。自愈次数用完的连接一直是"已坏"却显示"已连接"（SR:207），于是挡住所有兜底。
  - 换连接的结果被忽略（1517）。
  - connect() 关掉旧连接 600 毫秒后，如果 SDK 还没关完，会误报"已连接"（SR:139-141）。
  - connected() 不重置"上次收到状态的时间"（1675、780-804），回到前台时拿进后台之前的时间来算，于是误判。
- **安卓怎么做**：没有对应问题。安卓的 App Remote 不会这样"连着不干活"，出问题时重试，然后明确报错。
- **修法**：
  - 连接已坏，或刚换过连接时，开 4 秒轮询，直到新连接发来第一个状态再停。
  - 换连接失败时调用 connectHereOrPoll()。
  - connect() 关掉旧连接后，等它真的断开（设上限）再重连。
  - 连续两次不一致才换连接。新连接已经发过状态的，把间隔降到约 15 秒。
  - connected() 时把"上次收到状态的时间"设为现在；新连接还没满检测宽限期的，不检查。
  - 只有被换掉的连接曾经发过状态，才记下这次换连接的时间。
- **需要真机**：误判和关连接的时序问题要真机确认；主体不需要。

**#7 [P1] Yoin 在前台时 Spotify 被划掉、崩溃、更新或断开：Yoin 一直显示"播放中"、时间冻住，不重连也不提示**
- **用户会遇到**：Yoin 在前台，Spotify 被划掉、崩溃、更新、自己断开，或被系统挂起、换了账号。Yoin 还显示暂停按钮和这首歌，时间冻住（或者因为旧的 me/player 一直走过结尾）。Spotify 停了，Yoin 永远不更新；Spotify 还在放，换歌只能每 10 秒跟一次，期间歌词还是旧歌的。直到用户点了什么，才提示"打开 Spotify"。测试者反馈的第 3 个问题（歌放完不换下一首）在这条路径上还会出现。
- **原因**：
  - disconnected() 只把播放状态设成停、推一次时间，不通知播放引擎、不重连、不开轮询（SAO:1121-1125）。
  - 轮询只在 becameActive、connectHereOrPoll 失败、或目标是其他设备时才启动（1490-1498、1574-1578）。
  - watch() 在应用状态之前有"必须在播放"的条件，还会丢掉 204 空响应（1450、1461），所以暂停和停止永远不会被应用。
  - 结尾超时检查要求已连接（1926）。
- **安卓怎么做**：断开后发出 Idle/Error 状态，重试一次后显示"Spotify 播放连接已断开"（PlaybackManager.kt:1136-1152；SpotifyAppRemotePlayer.kt:1236-1241、1354-1430）。
- **修法**：在前台驱动本机时，只要 App Remote 断了（不是 Yoin 自己关的，也不是进后台），就：
  - 如果原本在播，通知引擎"已暂停"；
  - 调用 connectHereOrPoll()，4 秒轮询能应用 204 和暂停；
  - 尝试重连一次。
  - watch() 在驱动本机且没连接时，也要应用暂停和 204。
  - 仍然连不上就停在"打开 Spotify"状态。
- **需要真机**：触发方式建议真机确认；代码逻辑不需要。

**#8 [P1] App Remote 连不上时（测试者 build 28 的情况），每次换歌都把 Spotify 拉到前台再跳回来，Yoin 的队列推不动（eec6dca4 修得不完整）**
- **用户会遇到**：用户在 Yoin 看歌词，歌放完了：Spotify 先自动放一小段推荐，接着 Yoin 打开 Spotify 再跳回来。每首歌都有两次没人要求的切换 App。也可能 Yoin 直接标"队列结束"，或停在 0:00。几秒内重复点歌也会每次弹一下。连接只是慢（超过 1.5 秒）也会弹。在后台则完全不换歌。
- **原因**：
  - startHere 连接 1.5 秒失败就直接唤醒，也就是切到 Spotify App（SAO:419-437）。不区分是用户点的还是自动换歌；"本次已唤醒"的标记每次加载都重置（210）。
  - 连不上时 enqueueNext 要求已连接（704），所以下一首从来没交给 Spotify。到结尾要么判成"队列结束"（1809），要么走"Spotify 接着放了"分支，触发加载，又一次唤醒（1842-1846）。
  - 轮询只在前台进行（1547）。
- **安卓怎么做**：reportUnreachable 只在哪儿都没在放、用户点了、且 Yoin 在屏幕上时，最多打开一次 Spotify（SpotifyAppRemotePlayer.kt:1505-1544）。
- **修法**：
  - 引擎自己发起的加载（自动换歌、出错后跳歌）在 App Remote 连不上时绝不唤醒：停住并提示"在本机打开 Spotify"，或者把 Spotify 自己在放的歌当外部歌跟着显示。
  - 跨加载记下上次唤醒的时间，约 8 秒内只重试连接，不再唤醒。
  - 下一首从没交接过时，结尾按"放完一首、接着下一首"处理，而不是"队列结束"（见 #15）。
  - 用 Web API 往本机的 Spotify 队列加歌，要先真机验证。
- **需要真机**：需要（确认用 Web API 往本机队列加歌是否安全）。

**#9 [P1] 暂停很久后按播放：先报错，第二次点才行；从提示里打开 Spotify 回来后还得再按一次**
- **用户会遇到**：暂停后去做别的事（iOS 会挂起暂停中的 Spotify），回来点播放：出现错误横幅，保持暂停，再点一次才唤醒 Spotify。从横幅点"打开 Spotify"再回来，也还要再点一次播放。
- **原因**：播放命令先试连接 1.5 秒，失败后试 Web API（要求 me/player 指向本机，而且对被挂起的 App 无效），再失败就记为失败（SAO:1324-1350），这次播放命令被丢掉。只有第二次点击会走重试、重新加载、唤醒这条路（PE:217-218、436-441；SAO:436）。
- **安卓怎么做**：不会自动打开 Spotify，但会把这次"继续播放"留着。用户从提示里打开 Spotify 回来，如果 Spotify 是暂停状态，就执行它（SpotifyAppRemotePlayer.kt:1505-1544、1562-1587）。
- **修法**：两份审计给的方向相反，**建议按安卓做（方案 b）**。
  - (b) 留一条待执行的"继续播放"。横幅的"打开 Spotify"被点时打个标记；回来第一次连上时，如果 Spotify 停在当前歌的暂停状态，就执行，否则丢掉。
  - (a) 也可以：用户亲手点播放、连不上而且 Web API 也失败时，直接唤醒并带上当前位置，开播后跳回原位置。只用于用户操作，不用于自动换歌。注意唤醒会从 0 开始放，必须跳回去。
- **需要真机**：需要（被挂起的 Spotify 是否拒绝连接，唤醒后跳位置的体验）。

**#10 [P1] 本机播放时中途改队列被忽略：到点 Spotify 放的还是原来的下一首，Yoin 队列停泊**
- **用户会遇到**：本机放 Yoin 的队列时，对某首点"下一首播放"、删掉或挪动下一行、打开随机或单曲循环。这首放完，Spotify 还是放改动前的下一首。Yoin 把它显示为"Spotify 自己的歌"（队列面板变成"Next in Spotify"），用户选的歌永远不会放，Yoin 的队列也不再往前走。
- **原因**：
  - 改动会触发重新交接，但本机分支调用 enqueueNext，而已经交接过一首时它直接返回（PE:301-414、477-484；SAO:1127、1145、704）。
  - 播放模式改动只在按专辑/歌单整体播放（context）时才生效（677-687）。
  - 歌曲边界只在"Spotify 放的正是已交接的那首，而且它还是引擎的下一首"时才前进（1819）。本机的跳转匹配永远为空（1223-1231），"Spotify 接着放了"的兜底又靠不可靠的上一位置（见 #11），最后落进外部分支（1852-1856）。
  - AppModel.enqueue 只改引擎自己的队列（AppModel.swift:811-831）。
- **安卓怎么做**：加入队列直接进 Spotify 自己的队列（PlaybackManager.kt:771-795；SpotifyAppRemotePlayer.kt:523-529），Spotify 下一首就放它。"下一首播放"对 Spotify 隐藏。播放模式直接发给 Spotify。
- **修法**：Spotify 放到"过期的已交接歌"时，当作"继续放引擎的下一首"：跳过它，或加载引擎的下一首，不要标成外部歌。配合 #4 的"临近结尾才交接"，交接之前的改动就不用纠正了。
- **需要真机**：不需要。

**#11 [P1] 判断"歌放完了 / Spotify 接着放了"时用的上一位置不可靠：本机上单曲循环只放两遍、停在 0:00 不前进；在音箱上或暂停之后又会误判，抢掉用户在 Spotify 里选的歌**
- **用户会遇到**：
  - 本机：(a) 单曲循环（或只有一首的列表循环）只放两遍，之后 Spotify 停下或放电台，第二遍也不算进历史。(b) 最后一首，或下一首没交接的歌放完，Spotify 回到 0:00，Yoin 显示停在开头，而不是前进或结束。(c) Spotify 越过这首放了意外的内容，Yoin 把它当外部歌，而不是放自己的下一首。
  - 反过来：(d) 在 Yoin 一首歌的最后 8 秒内暂停（或锁屏），去 Spotify 选了别的歌再回来，Yoin 认为自己那首"放完了"，在用户选的歌上开播自己的下一首。本机和音箱都会这样。
- **原因**：
  - 上一位置只在收到 Spotify 推送的状态时才更新（SAO:1753-1755），而 App Remote 只在状态变化时推送。所以本机上它是这首开头、或上次拖动/暂停时的位置，三个判断（1792、1801、1842）都失效。
  - 同时 1842-1846 不检查这个位置有多旧、当时是否在播、是否来自 App Remote。一个过时的"快到结尾"位置会被误判成"Spotify 接着放了"，于是 Yoin 开播自己的下一首。
- **安卓怎么做**：用挂钟时间从上次状态推算当前位置（PlaybackManager.kt:126-140、1165-1170）；循环交给 Spotify 自己（setRepeat）；从不因为 Spotify 报告换了歌就自己开播下一首。
- **修法**：
  - 用推算出来的当前位置作为上一位置（在覆盖之前取值）。
  - 记下这个位置是什么时候看到的。只有上次读取在约"轮询间隔 + 2 秒"以内、而且当时在播时，才算"Spotify 接着放了"；否则当作用户自己的选择，显示为外部歌。
  - 本机单曲循环且只有一首时，把 Spotify 的循环设成"单曲"，而不是反复塞同一首。
- **需要真机**：需要（确认本机结尾行为）。

**#12 [P1] Yoin 认不出 Spotify 队列里的其他歌：锁屏上的上/下一首、用户原本就有的 Spotify 队列、别人在音箱上加的歌，都会让 Yoin 队列停泊，或把别人的歌切掉**
- **用户会遇到**：
  - 本机：用锁屏卡片、AirPods 或控制中心按上一首/下一首；或者开播时用户的 Spotify 队列里本来就有歌（Spotify 先放这些，Yoin 的下一首排在后面）；或者冒出残留歌。Yoin 都显示成"Spotify 自己的歌"并停泊队列。之后就算 Spotify 放回 Yoin 队列里的歌，Yoin 也不再回去。
  - 音箱：家人在 Spotify 里给音箱加了歌，Yoin 的队列在那放。当前歌放完 Spotify 放他们加的歌，4 秒内被 Yoin 换成自己的下一首，他们加的每一首都被切掉。队列面板从来不显示这些歌。在音箱上按上一首，Yoin 把自己队列里的上一首当成外部歌。
- **原因**：
  - 唯一的前进条件是"Spotify 放的正是已交接的那首，也是引擎的下一首"（SAO:1817-1819）。
  - 跳转匹配只往后看已交接列表（本机上永远为空），不看上一首（1223-1233）。
  - 一旦标成外部，整个追赶逻辑都被挡住（1817）。
  - 音箱上不认识的歌在结尾附近会被当成"Spotify 接着放了"，于是 Yoin 换上自己的下一首（1842-1847）。
  - 从不读 Spotify 的用户队列，队列面板只列引擎的后续歌曲（QueueSheet.swift:42-88）。
- **安卓怎么做**：SpotifyQueueMirror.onPlaying/indexOf 在 Yoin 列表的当前、下一首、上一首以及任意位置查找（SpotifyQueueMirror.kt:155-214）。开播后约 800 毫秒读 GET me/player/queue，把用户已经排的歌显示在前面并跟着走（SpotifyAppRemotePlayer.kt:537-566；SpotifyQueueMirror.kt:105-150）。
- **修法**：
  - 把 Spotify 正在放的 uri 和引擎的后续列表、上一首做匹配，匹配上就跳到那里（包括已经标成外部之后，也包括往回跳）。
  - 每次开播后读 me/player/queue：第一首已交接歌之前的部分，当作 Spotify 用户队列，在面板里列出来；放到它们时只显示，不切掉。
  - 只有遇到两边都不认识的歌，才重新交接或当成外部歌。
- **需要真机**：不需要。

**#13 [P1] 3dd4c82c 之后，只要 Spotify 在放 Yoin 认为是"外部"的歌，队列面板就把 Yoin 停泊的队列整个藏起来，用户点不回自己的专辑（回归）**
- **用户会遇到**：发生了上面任何一种停泊（本机上很常见），用户打开队列面板想回到专辑，只看到只读的"Next in Spotify"（常常是电台或残留歌）。专辑的歌一行都没有，也点不了，只能重新找到专辑再放。
- **原因**：只要当前是 Spotify 外部歌，QueueSheet 就只显示 Spotify 列表，不包含 Yoin 的队列（QueueSheet.swift:29-40、108-128）。3dd4c82c 之前，面板总是显示可以点的 Yoin 队列。
- **安卓怎么做**：保留 Yoin 的队列，把外来的歌插在 Spotify 实际放的位置；点某一行就从那里重新开始（SpotifyQueueView.foreignIndex；SpotifyAppRemotePlayer.kt:604-620）。
- **修法**：Yoin 队列不为空时，显示可以点的 Yoin 队列（外部歌作为"正在播放"），下面加一个只读的"Next in Spotify"分组。只有 Yoin 没有队列（纯陪伴模式）时，才只显示 Spotify 列表。
- **需要真机**：不需要。

**#14 [P1] Spotify 放的是按地区换过的副本（同一首歌在 Spotify 里换了个 id）时，Yoin 从第一秒起就把它当成"Spotify 自己的歌"：队列停住，评分和笔记记到别的 id 上**
- **用户会遇到**：有些地区的专辑或合辑歌（日本账号很常见），Spotify 实际放的是另一个 id 的副本。用户在 Yoin 点播，歌能放，但 Now Playing 立刻进入"Spotify 自己的歌"模式：上/下一首走 Spotify，下一首不交接，放完 Spotify 放电台，或 Yoin 从头重放。评分、笔记、歌词缓存都记到副本的 id 上，而不是资料库里那首。
- **原因**：
  - 向 Spotify 查歌曲目录时不带地区参数（Data/Spotify 下没有 market），所以 Yoin 放的是原 id。
  - 副本的 id 只能从 Web API 的 linked_from 学到（SAO:502、1702），而 App Remote 连着时本机不走那条路（1457-1460、1595）。
  - App Remote 的第一个状态 uri 和当前歌对不上，直接进外部分支（1852-1856）。塞下一首要求 uri 对得上（693），下一首的副本也匹配不上（1819）。
- **安卓怎么做**：按"标题 + 艺人"匹配副本（spotifyPlays，SpotifyAppRemotePlayer.kt:1312-1322；isSameSongAs，SpotifyContextSync.kt:263-269）。
- **修法**：
  - 判成外部歌之前，先按 uri、再按"标题 + 第一艺人"（不区分大小写）和当前歌、已交接的歌匹配；匹配上就记下副本 id，当作当前歌处理。
  - 评分、笔记、Now Playing 数据一律用队列里那首的 id。
  - 查目录时带上 market=from_token，让大多数 id 一开始就是本地区能放的。
- **需要真机**：需要（确认出现频率）。

**#15 [P1] 下一首可能根本没交给 Spotify；这时这首放完会被当成"整个队列结束"**
- **用户会遇到**：从 Yoin 开播专辑后一两秒内锁屏或切 App，或者开播时连接短暂坏掉：Spotify 放完这一首就停（或放电台）。如果停了，Yoin 把整个队列标成结束，尽管专辑还有歌。
- **原因**：
  - 开播成功后只设了"等在播时再塞"的标记（SAO:670）。真正塞下一首，要等到一个"正是这首、在播、位置大于 0"的推送状态（693、1759）；开播期间收到的状态被丢掉（1758），也没有定时兜底。
  - 进后台断开之前不尝试塞（884-888）；连上时、回前台重连时也不补塞（780）。
  - 没连接时 enqueueNext 默默返回，也不记下"下一首没交出去"（704）。
  - 结尾判断：记着"没交出去"才接着下一首，否则判"队列结束"（1805-1809）。
  - 交接成功前进时补塞的那一刻，恰好是 App Remote 以前回过 -3000 错误的时刻（1825）。
- **安卓怎么做**：把整张专辑/歌单/列表作为一个整体交给 Spotify 开播，不依赖一首一首塞队列（PlaybackManager.kt:556-585）。
- **修法**：开播成功后用短定时器重试塞队列；每次连上或重连、而下一首还没交出去时补塞；进后台时在 beginBackgroundTask 保护下补塞。结尾判断改成：只要下一首还没交出去、而引擎还有下一首，就接着放下一首。
- **需要真机**：需要（确认出现频率）。

**#16 [P1] 锁屏期间 Spotify 放过两首以上，回到 Yoin 时状态错误：停在第一首，或显示"播放中"其实已经停了**
- **用户会遇到**：
  - 从 Yoin 放专辑后锁屏，Spotify 放了 A、B（唯一交接过的那首）后停下（自动播放关）或放电台（默认开）。
  - 开着自动播放：回来时 Now Playing 把电台歌显示成外部歌，专辑停在 A（连 B 都不是），队列面板只有电台。
  - 关着自动播放：Yoin 跳到 B，显示暂停按钮（即"播放中"），时间停在 0:00，其实没在放；它还往已经停下的 Spotify 里塞了 C，按播放可能放 B 也可能放 C。
  - 或者 Spotify 前进到 B 后用户在锁屏上暂停了：回来显示 B、暂停按钮、时间不走，要多点一次才能播放；时长显示的还是上一首的。
  - 锁屏期间放过的歌都不算进历史。
- **原因**：
  - "交接成功、前进到下一首"的分支在同步播放状态和"停在结尾"检查之前就返回了（SAO:1819-1825 对比 1811-1814）。这时 Yoin 内部已经认为没在放（1757），引擎却还以为在放。
  - 时长只在"还是当前这首"的分支里更新（1785-1789）。
  - 接着又往已经停下的 Spotify 塞了 C。
  - 电台歌落进外部分支（1852）。
  - 计播放时长的逻辑把这种大跨度跳跃当成拖动，不计入（PE:556-560）。
- **安卓怎么做**：Spotify 手里有整个列表，回来时仍在 Yoin 的队列里，镜像跟上就行（SpotifyQueueMirror.onPlaying）。
- **修法**：前进分支里也应用新歌的时长，并同步播放状态。把回到前台后的第一个状态当作"追赶"：Spotify 已经越过或停在已交接的那首时，把引擎移到它之后那首；Spotify 停在结尾时不塞队列。
- **需要真机**：需要。

**#17 [P1] 锁屏听歌：本机从 Yoin 放的专辑/歌单只放两首就停；能解决这个问题的"整体交给 Spotify 播放"（context 开播）默认是关的**
- **用户会遇到**：最常见的用法：在 Yoin 打开专辑点一首，然后锁屏。只放这首和下一首，之后停下或进入 Spotify 自动播放。锁屏上按上一首、或连按两次下一首，会让队列永久停泊。安卓在后台能放完整张专辑。
- **原因**：
  - 是否按 context 开播，读的是一个 QA 测试用的启动参数（SAO:440-444），所以本机总是"单首开播 + 塞一首下一首"（419-437、462-475、703-729）。
  - 进后台时断开 App Remote（884-888）。
  - docs/spotify-background.md 写的是"build 12 起默认关"，列为已知限制。
  - 就算打开：随机播放时 Spotify 自己定顺序，而 Yoin 显示的是自己打乱的顺序；按 context 播放时改队列的处理依赖 #11 的上一位置。
- **安卓怎么做**：专辑、歌单、"喜欢的歌"都整体交给 Spotify 开播（SpotifyAppRemotePlayer.kt:400-415；SpotifyStartPlan.kt）。
- **修法**：
  - 先修 #11；随机播放时读 me/player/queue，显示 Spotify 的真实顺序。
  - 真机跑一遍 context 开播（playContext + skipToTrackIndex）。build 11 的失败是唤醒时序问题，build 12 已经另外修了。通过后，对专辑和歌单页默认打开。
  - 零散列表保留"塞一首下一首"。这个不能去掉，它是锁屏后唯一能接到下一首的办法。同时让本机的跳转匹配接受引擎的上一首。
  - 在那之前，把这个限制写进 qa-script.md 和应用内帮助。
- **需要真机**：需要。

**#18 [P1] 在 Spotify 里放的歌（以及 Yoin 标成"外部"的歌、锁屏或后台期间放的歌）不进历史、回忆、播放次数、首页动态、Play 小组件，也不 scrobble**
- **用户会遇到**：典型的陪伴用法：在 Spotify 里开歌，Yoin 开着看歌词、打分、写笔记一小时。最近播放、播放次数、回忆、首页动态、Play 小组件里一首都没有，只有从 Yoin 开播的才有记录。再加上前面各种停泊，本机上相当大一部分收听都没被记录。音箱上锁屏期间放的歌也没有。
- **原因**：
  - 播放开始和播放计数这两个函数都要求"当前不是外部歌"（PE:545-573），时间更新对外部歌也提前返回（671-676）。而 onScrobble 是写入历史的唯一入口（AppModel.swift:364-369）。
  - 跳转时直接跳到目标那首，中间的歌不记录（PE:645-664）。
  - 小组件只从历史生成（WidgetPublisher.swift:73-87）。
- **安卓怎么做**：recordPlayIfDue 记录 Spotify 正在放的每一首，包括在 Spotify 里开播的（PlaybackManager.kt:1303-1327），也会进小组件。
- **修法**：
  - 给外部歌单独维护一份按歌曲 id 的计数状态，外部歌换了就重置。在播时先记一条，达到时长门槛后再标记计入。不动停泊那首歌的计数。recordHistory 已经按歌去重（LibraryStore.swift:1558-1576）；LibraryStore.scrobble 已经会跳过非 Subsonic 的歌。
  - 回到前台、且有 Spotify 在播时，读 GET me/player/recently-played?after=<进后台的时间>，补记这段时间放过的歌。
- **需要真机**：不需要。

**#19 [P1] Now Playing 的爱心（喜欢的歌）不刷新：在 Spotify 里点的喜欢或取消，在 Yoin 里永远看不到**
- **用户会遇到**：Spotify 在放，Yoin 显示空心。用户在 Spotify App、锁屏或车机上点了喜欢，回到 Yoin 还是空心，整个会话都不变。反过来在 Spotify 取消喜欢，Yoin 一直是实心。在 Yoin 里点过一次爱心之后，这首歌就永远钉在那个状态。专辑页 2 小时内的缓存也显示旧爱心。
- **原因**：
  - 只在还没有答案时问一次"是否已喜欢"（NowPlayingData.swift:131-143）。爱心状态存储只保留第一个答案，没有地方允许覆盖（FavoritesStore.swift:44-48）。
  - isSaved 直接从内存里的"已喜欢"集合返回 true（SpotifySource.swift:490-491）。
  - 显示优先级是"用户刚点的 > 缓存值 > 新查到的"，缓存值压过新答案（FavoritesStore.swift:34-37；LibraryStore.swift:1440-1450）。"用户刚点的"写入成功后从不清除。
  - 专辑页 2 小时内不复查（LibraryStore.swift:787-792）。
  - 没用 App Remote 的 fetchLibraryState。
- **安卓怎么做**：SpotifySavedStateRefresher 每次换歌查一次，之后的状态事件（暂停、拖动、回前台重连）最多每 30 秒再查一次，先问 App Remote，不行再用 Web API（SpotifySavedStateRefresher.kt:23-87；PlaybackManager.kt:1676-1686）。专辑页每次打开都复查。
- **修法**：
  - 照搬 SpotifySavedStateRefresher：换歌时、之后最多每 30 秒用 App Remote 的 fetchLibraryState 查一次；Web API 只在换歌约 800 毫秒后兜底。查到的结果要能覆盖旧答案。
  - 回到前台且当前是 Spotify 歌时复查。
  - "用户刚点的"写入成功后清掉。
  - isSaved 不再从内存集合直接返回；显示时优先用比缓存值更新的答案。
  - 专辑页打开时重查（限频）。
- **需要真机**：不需要。

**#20 [P1] Spotify 在放它自己的歌时，"加入队列"经常失败（App Remote 没连上、连接坏了、在音箱上则一定失败）；▾ 菜单还显示做不到的"下一首播放"**
- **用户会遇到**：Spotify 在放它自己的歌，用户刚回到 Yoin（连接还在建立），或 App Remote 连不上（build 28 测试者），或 Spotify 在投音箱：对任何歌点"加入队列"都提示"无法加入队列"。连接坏了却显示已连接也会失败，而且不重试。专辑/歌单页的 ▾ 菜单还有"下一首播放"，这种情况下永远做不到，也报"无法加入队列"。加成功了，"Next in Spotify"也不显示新加的歌，要等换歌。
- **原因**：
  - enqueueOnSpotify 一开头就要求"在本机且已连接"，否则直接失败；不重连、不看连接是否已坏、也没有 Web API 的办法（SpotifySource 没有 POST me/player/queue）（SAO:738-750）。
  - 外部歌时 AppModel 把加队列都发到这里，并拒绝"下一首播放"（AppModel.swift:817-823）。
  - ShellBar.swift:361 和 PadShell.swift:549 仍然显示"下一首播放"（TrackMenuSheet.swift:352 已经隐藏了）。
  - 队列面板只在换歌时重读（QueueSheet.swift:127）。
- **安卓怎么做**：addToQueue 经 enqueueOperation 先连接再执行，然后 syncQueueWithSpotify 重读队列；投屏时 App Remote 也能用；Spotify 下隐藏"下一首播放"（SpotifyAppRemotePlayer.kt:523-530；PlaybackManager.kt:787-796）。
- **修法**：
  - enqueueOnSpotify 像 command() 一样等待连接，连接坏了重试一次。
  - App Remote 连不上，或目标是其他设备时，用 Web API POST me/player/queue?uri=…&device_id=…。这属于产品规则允许的"加入队列"。
  - 成功后让面板重读。
  - 当前是外部歌时，▾ 菜单隐藏"下一首播放"。
- **需要真机**：部分需要（本机连不上时用 Web API 加队列是否安全，同 #8）。

**#21 [P1] 音箱暂停时按下一首/上一首/点队列里的一行，音乐会跑到 iPhone 上，还可能把 Spotify App 拉到前台**
- **用户会遇到**：Yoin 的队列在音箱上放，暂停后按下一首（或上一首、点队列面板的一行）：歌被转到 iPhone，设备胶囊从音箱名变成"设备"。如果手机上的 Spotify 睡着了，Yoin 会切到 Spotify App，歌在手机上响一下再被暂停。音箱在放时，只要一次 me/player 读取失败（超时或限流）也会这样。音箱放完列表停下后自动换歌，也一样。
- **原因**：每次换歌 start() 都重新选目标设备（SAO:246-261）：
  - 只接受正在放的设备（977-980），读取失败被当成"哪儿都没在放"（248）；
  - 于是清掉目标和设备名（257-259），把 Spotify 转到手机（286-305）；
  - 没连接就唤醒（436）；
  - 开播之后才暂停（662）。
- **安卓怎么做**：skipNext/skipPrevious 经 App Remote 发给 Spotify，留在 Spotify 当前的设备上；只有全新开播才去手机（SpotifyAppRemotePlayer.kt:475-485；PlaybackManager.kt:1438-1449）。
- **修法**：
  - 正在进行的播放（下一首、上一首、队列跳转、自动换歌、重试）里，只要上次 me/player 显示那个设备是活动的（不管在放还是暂停），就保留它作为目标，并按正确的播放/暂停状态发开播。
  - "只有正在出声的设备才保留"这条，只用于没有正在进行的播放、从页面全新开播时。
  - me/player 读取失败重试一次，还失败就沿用上次已知的目标。
- **需要真机**：不需要。

**#22 [P1] 在音箱上放时改队列或切随机，然后锁屏：Yoin 丢掉自己的队列，加的歌永远不放**
- **用户会遇到**：Yoin 的队列在音箱上放，一首歌放了 3 秒以上后加入队列（或排序、删除、切随机/循环），然后锁屏。音箱按旧列表继续放，加的歌永远不放。回到 Yoin，音箱上的歌显示成"Spotify 自己的歌"，面板变成只读的"Next in Spotify"，Yoin 的队列从此卡在旧歌上。
- **原因**：
  - 放了 3 秒以上的改动只设一个"交接已过期"的标记（SAO:1139-1167、1215），而这个标记从来没有被读取过（只在 64、205、929、1152、1156、1642 行写）。
  - 进后台时停轮询（884-888），换歌时没人读状态。
  - 回来后跳转匹配要求已交接列表和改过的队列开头一致（1223-1233）；上一位置又是进后台之前的，最终落进外部分支（1852-1856）。
- **安卓怎么做**：不需要重新交接。改动直接进镜像，App Remote 报告每一首，onPlaying 在 Yoin 列表里找到它（SpotifyQueueMirror.kt:161-175）。
- **修法**：
  - 不要在进后台时按当前位置重新交接，那会让歌从中间重新开始，违反"不切入正在放的歌"的原则。
  - 回来时，只要 Spotify 的歌在引擎的后续列表（或旧的已交接列表）里，就跳过去，然后在新歌开头（3 秒内）或下一个歌曲边界重新交接。
  - 单纯的"加入队列"可以同时用 POST me/player/queue 发给目标设备，这样在后台也能生效。
  - 删掉那个没人读的标记，或者用它在回到前台时强制读一次状态。
- **需要真机**：不需要。

**#23 [P1] 从 iPhone 把播放转到音箱后（设备面板或 Spotify 的设备选择器），Yoin 的队列在下一首之后就停了**
- **用户会遇到**：本机从 Yoin 放专辑，然后在设备面板或 Spotify 里转到音箱：当前这首和下一首能放，之后音箱停下，Yoin 说队列结束，或显示停在 0:00。开着自动播放的话，Spotify 先放最多 4 秒推荐，Yoin 才切进来。

- **修法**：重新交接的时机判断里，"已交接列表为空、新列表不为空"且这首刚开始 3 秒内时，立即交接。结尾时，目标是远程设备且下一首没交出去，就接着放下一首（引擎没有下一首时本来就会结束）。要和 #21 一起修，否则 start() 会把停下的音箱当成空闲，把音乐拉回手机。
- **需要真机**：不需要。

**#24 [P1] Spotify 官方歌单（Discover Weekly、Daily Mix、Today's Top Hits 等）打开是空页**

**#25 [P2] App Remote 连接失败不区分原因：一律唤醒 Spotify，或提示"打开 Spotify"**
- **用户会遇到**：Spotify 没登录、需要更新、离线、或拒绝 Yoin 的 token/Client ID 时，Yoin 每次都打开 Spotify（或说"打开 Spotify 再点播放"），这些都解决不了问题。用户来回折腾，不知道真正的原因。测试者的"10 毫秒连接失败"就是这种。
- **原因**：连接失败回调只留下一段描述文字（SR:496-501），往上只传"成功/失败"（357-363）。调用方要么唤醒（SAO:434-436），要么提示"打开 Spotify"（1345）。eec6dca4 新记下的错误类型和错误码没被用上。

- **修法**：先从测试者那里收集 eec6dca4 记下的错误类型和错误码。然后让连接返回带类型的结果，只映射已经确认的错误码：认证或 token 被拒，去"设置 › Spotify"；Spotify 睡着或超时，才唤醒。其他情况停在当前歌，配各自的文案。在那之前，同一账号已经发生过一次 100 毫秒以内的快速失败后，不再唤醒。
- **需要真机**：需要。

**#26 [P2] App Remote 用的 token 和 Client ID 可能和 Spotify 认可的不一致：跳回时拿到的 token 被覆盖，Client ID 读的是全局或同步来的设置**
- **用户会遇到**：唤醒后跳回，带回了一个能用的 token，连上了。下次连接（每次回到 Yoin、每次重连）Yoin 又换回 Web API 的 token；如果 Spotify 不认它，之后每次连接都快速失败，只有再唤醒才行。在设置里或通过云同步改了 Client ID 之后，也会这样。
- **原因**：
  - 每次连接都把 token 换成 Web API 的（SR:142），覆盖了 259 行跳回时拿到的 token；取 token 失败时默默留着旧的。
  - App Remote 用的是全局的 Client ID（SR:91、118-126），它可能被 ServiceSetupView.swift:541 和 SyncDomainBridge.swift:439-444 改掉；而刷新 token 用的是账号里保存的 Client ID（SpotifyAuth.swift:174）。
  - 跳回时，回前台的连接和处理跳回链接的连接紧挨着各连一次。
- **安卓怎么做**：没有对应问题。安卓经 Spotify App 授权，不传 Web API 的 token。
- **修法**：把当前账号保存的 Client ID 传给 SpotifyRemote。保留并优先用跳回时拿到的 token，直到它失效。已经有连接在等待时，处理跳回链接不再另外发起连接；有更新的跳回 token 时，连接时不覆盖它。
- **需要真机**：需要（Spotify 是否拒绝 Web API 的 token，还没有证实）。

**#27 [P2] 回到 Yoin 时，歌词和时间先跳回 App Remote 上次报告的位置并冻住；App Remote 慢或连不上时要 4–6 秒才更新**
- **用户会遇到**：Yoin 在前台听了几分钟没碰，锁屏再打开：歌词和时间跳回上次报告的位置（常常是这首开头），按钮还显示"播放中"，直到新连接的第一个状态到来（通常 1 秒内）。连接慢或连不上时，显示的还是离开时的歌和歌词，冻住 4–6 秒（用户在 Spotify 里换了歌也看不到）。这时写的笔记会记在过时的时间点上。在前台被 Spotify 断开也会跳回。安卓是立刻读取的。
- **原因**：
  - 进后台时断开连接没有标记"这是 Yoin 自己关的"（SR:228-231），于是走进 disconnected()，它不先算好当前位置，就把状态设成停并推送旧位置（SAO:1121-1125）。
  - becameActive 立刻发起的那次 watch 读取，在轮询启动后被丢掉（1451、1574-1578）；轮询启动时不立刻读（1543-1548）；connectHereOrPoll 还要再等 1.5 秒（1490-1498）。
- **安卓怎么做**：onHostStart 立刻轮询或刷新（SpotifyAppRemotePlayer.kt:318-337）；位置一直从上次状态往后推算（PlaybackManager.kt:1062-1078）。
- **修法**：disconnected() 里先把位置更新成推算的当前位置。进后台断开时标记为 Yoin 自己关的（或者在后台时忽略断开）。becameActive 在本机且没连上时，开轮询后立刻读一次。watch 的答案如果是在轮询开始前发起的，也允许应用。
- **需要真机**：不需要。

**#28 [P2] 在 Spotify 自己的设备选择器里投到音箱再切回 iPhone，之后轮询一直不停，挡住"连着不干活"的检测和结尾检测**
- **用户会遇到**：测试者有时会投屏。在 Spotify 里转到音箱再转回手机，Yoin 一直开着。之后如果 App Remote"连着不干活"，歌放完又会停在 -0:00，因为 3dd4c82c 的检测要等 Yoin 进出一次后台才恢复。
- **原因**：设备变成别的时会开轮询，但 me/player 再指回本机时从不关掉（SAO:1715-1719）。只有 followTransfer（870-882）和连接成功会关。watch() 要求没在轮询（1447、1451），连带结尾超时触发的 watch 也失效；而已连接时轮询本身什么都不做（1595）。
- **安卓怎么做**：回到 App Remote 所在的设备时，exitWebMode 停止 Web 轮询（SpotifyAppRemotePlayer.kt:1649-1665）。
- **修法**：apply(now) 发现设备变回本机（不是 Mac）时，停掉轮询，再调用 connectHereOrPoll()。
- **需要真机**：不需要。

**#29 [P2] "本机"只靠 Spotify 设备名里有没有"iPhone"来认：改过名的 iPhone 被当成远程设备，同一账号的另一台 iPhone 被当成本机**
- **用户会遇到**：iPhone 改过名（比如"小明的手机""Work phone"）：
  - "连着不干活"的检测不运行；App Remote 不通时拖动/暂停/切歌提示"打开 Spotify"，而不是走 Web API。
  - 更糟的是会把本机当成远程设备，对本机 id 发 Web API 开播/暂停/拖动。文档说这会把 Spotify 踢下 Connect，出现"找不到设备"，胶囊把手机当音箱显示。
  - 同一账号另一台名字带"iPhone"的旧手机在放时，被当成本机，Yoin 去用 App Remote，而不是遥控它。
- **原因**：识别本机的规则要求"类型是手机且名字含 iPhone"（SpotifyThisDevice.swift:48-53）。这一条判断决定了：选哪个远程目标（SAO:977-980）、watch 和接管（1457、1472-1475）、跟随设备（1717）、followTransfer（872）、Web API 兜底（1356）、开播落点确认（521-524）。判错时会对本机发开播（895-960）。
- **安卓怎么做**：用用户设置的设备名和机型精确匹配（PlaybackManager.kt:1511-1517；SpotifyMusicSource.kt:812-816）。
- **修法**：只在确定是本机时学习本机的 Connect id：转到本机成功且 me/player 指向这个 id 之后，或者没有远程目标、用 App Remote 开播后 me/player 显示一台放同一首的手机。按账号保存，优先按 id 匹配，名字规则只作后备。永远不对保存下来的本机 id 发 Web API 开播。注意：iOS 上 Spotify 在遥控音箱时 App Remote 也会报告播放，不能只凭这一点判断是本机。
- **需要真机**：需要（Spotify 给 iPhone 报的名字是什么）。

**#30 [P2] eec6dca4 给本机加的 Web API"继续播放"，用的正是曾经把本机踢下 Connect 的那类请求**
- **用户会遇到**：App Remote 连不上（build 28 测试者），点播放让 Spotify 自己暂停的歌继续：Yoin 发 PUT me/player/play?device_id=<本机>。如果它和 11-06 日志里的开播请求一样，Spotify 就会掉线：me/player 返回空、之后命令 404，用户只能自己去开 Spotify。
- **原因**：本机的继续播放走 Web API 的 resumePlayback 并带上本机 id（SAO:1241-1259；SpotifySource.swift:361-364）。文档只记录了带歌曲列表的开播会踢掉本机（docs/spotify-background.md:21-24），不带歌曲的继续播放没测过。暂停中的 Spotify 被挂起时，继续播放也可能直接失败。

- **修法**：me/player 已经显示本机是活动设备时，继续播放不带 device_id（纯继续，不涉及转移设备）。真机测试；如果失败，或之后 me/player 返回空，显示"打开 Spotify"而不是重试。暂停、拖动、切歌继续走 Web API。

**#31 [P2] 打开 Yoin 时 Spotify 在本机处于暂停：Yoin 什么都不显示**
- **用户会遇到**：一分钟前在 Spotify 暂停了，打开 Yoin 想给这首打分或写笔记：Yoin 是空闲的（或显示旧队列），要等 Spotify 再放才接上。
- **原因**：接管只在 watch() 里做，而且前面要求"正在播放且有歌"（SAO:1461、1466-1480），暂停的本机还常常返回空。空闲时回前台直接返回，不去连 App Remote（1558、1576）。
- **安卓怎么做**：warmConnection 在 App 启动时就连 App Remote，第一个状态（包括暂停）就接管显示（PlaybackManager.kt:1149-1155；SpotifyAppRemotePlayer.kt:363-383）。
- **修法**：空闲、在前台、Spotify 账号在用、而且装了 Spotify 时，悄悄尝试连接 App Remote（不唤醒、不提示、失败就算了）。第一个带歌的状态按 watch 的方式接管，不发播放命令，显示为暂停。watch() 也允许接管指向本机的暂停状态。iOS 的限制：被系统挂起的 Spotify 可能拒绝这种连接，所以只覆盖刚暂停不久的情况。
- **需要真机**：需要。

**#44 [P2] 遥控音箱（或本机 App Remote 不通、走 Web API）时，暂停/播放/拖动会回弹**
- **用户会遇到**：Spotify 在音箱上，Yoin 当遥控：点暂停，按钮变成播放，约半秒后又变回暂停、时间继续走，约 4 秒后才稳定为暂停；点播放同理。点歌词，歌词跳过去、弹回原处、下次轮询再跳过去。本机 App Remote 不通时也一样，这会让测试者"点歌词不跳"的问题在这条路径上重现。
- **原因**：每次 Web API 命令之后 0.6 秒都会读一次 me/player（SAO:1394-1425、1423、1371），4 秒轮询照常；读到的播放状态和位置直接采用（1754-1757），对不上就把"想要播放"翻过去（1812-1815）。只有开播落地时有保护（1690-1701）。代码自己也写着 me/player 会落后（1503-1508）。
- **安卓怎么做**：全部走 App Remote，没有轮询旧状态（SpotifyAppRemotePlayer.kt:461-491）。
- **修法**：每次 Web API 拖动/暂停/继续后，记下目标状态和时间。约 3 秒内，忽略和它矛盾的同一首歌的读取（播放状态相反，或位置离"目标 + 已过时间"超过约 1.5 秒）。遇到一致的读取、换歌、或时间到了，就解除。不为此取消或提前常规轮询。读到的是别的歌或别的设备，照常应用。
- **需要真机**：需要。如果真机日志证实，本机这条路径可以升成 P1。

**#45 [P2] 音箱换歌时"按预计结尾读一次"总被下一次轮询取消：改过队列后，错的歌会放最多 4 秒；每次换歌 -0:00 冻住最多 4 秒**
- **用户会遇到**：中途加了歌之后，当前歌放完时音箱先放旧的下一首，0.5–4 秒后 Yoin 才换成对的。每次换歌还会显示旧歌 -0:00、歌词停在结尾，最多 4 秒。
- **原因**：重新交接时安排的结尾读取（SAO:1157）和轮询共用同一个任务位，每 4 秒的轮询会先把它取消（1596、1543-1548）。文档 spotify-background.md:30 说的"结尾时读一次"实际上不成立。结尾超时检查只对本机（1926-1931），而且它调用的 watch() 在轮询时直接返回（1447）。
- **安卓怎么做**：App Remote 立即推送换歌。
- **修法**：结尾读取单独用一个任务，不被轮询取消；远程目标每首都在预计结尾后 0.4 秒读一次、再过 1.5 秒读一次。远程时，超时检查直接读一次状态。
- **需要真机**：不需要。

**#46 [P2] 受限设备（比如 Sonos）也被当成可以用 Web API 控制：暂停/拖动悄悄失败，开播显示 Spotify 的原始错误**
- **用户会遇到**：Spotify 在 Sonos 上，Yoin 当遥控：暂停看似成功，下次轮询又变回播放，没有提示；点歌词无效，时间停一下；在 Yoin 点歌显示 Spotify 原始的"Restriction violated"或 403。没有任何地方告诉用户要去 Spotify 里控制那个音箱。
- **原因**：读 me/player 时不读"设备受限"字段（SpotifySource.swift:282-302）；任何有 id 的设备都会被选作目标或接管（SAO:977-980、1474）；暂停和拖动失败不报告（1115、1296）；命令失败时一律把状态设成"没在放"，包括拖动失败（1413）；开播错误直接显示原文（943-959）。设备面板其实知道哪些设备受限（SpotifySource.swift:412-420；SpotifyDevicesSheet.swift:31）。

- **需要真机**：需要。

**#47 [P2] Spotify 转到没有 id 的音箱（Sonos、Cast）时，Yoin 继续把命令发给上一个设备**

**#48 [P2] me/player 有设备却没有歌（播客，可能还有隐私会话）时：Yoin 显示暂停，或说音箱"停止了这首歌"，点"重试"把播放拉到手机上**

**#49 [P2] 音箱关机或被 Spotify 踢掉后：胶囊还显示它的名字，点播放报错，点"重试"却悄悄在手机上放**

**#50 [P2] 慢音箱开播时误报"停止了这首歌"或闪一下上一首；开播期间按的暂停会丢**
- **用户会遇到**：给 Sonos 或 Cast 选一首歌（切换要 3–6 秒）：Yoin 先把上一首显示成"Spotify 自己的歌"（面板变成"Next in Spotify"，下一首按钮跳的是 Spotify 的列表），或显示"X 上的 Spotify 停止了这首歌"然后又消失。开播后马上按暂停会被丢掉，歌开始放后 Yoin 又变回播放。

- **安卓怎么做**：开播期间一直显示用户点的那首，直到 App Remote 确认；排队的操作不会丢（SpotifyAppRemotePlayer.kt:345-433）。
- **修法**：开播检查也要连续两次空响应才算失败。等待开播期间显示待放的歌，而不是把旧歌当外部歌。开播结果不明确时，保留排队的暂停/拖动，等第一次看到这首歌时执行。
- **需要真机**：需要。

**#51 [P2] 发给音箱的命令可能乱序；网速慢时轮询互相取消，Yoin 完全不更新**
- **用户会遇到**：快速点暂停再点播放，或连点两句歌词：音箱可能停在第一个状态，而 Yoin 显示第二个。移动网络慢时（响应超过 4 秒），Yoin 当遥控完全不更新（歌、时间、暂停状态都不变），音箱照常放。
- **原因**：每条命令各自开一个任务发出，没有先后顺序（SAO:1394-1425）。每次 4 秒轮询都会取消上一次还在等网络的读取（1596），而网络请求会响应取消，于是慢的响应永远到不了。
- **安卓怎么做**：命令一条一条执行（SpotifyAppRemotePlayer.kt:461-491），也没有播放轮询。
- **修法**：远程命令排成一队顺序发；多次拖动只发最后一次；暂停后紧跟着播放时，丢掉排队的暂停。还在进行中的轮询读取不取消，跳过这次新的轮询。限流时命令被悄悄延迟 15–30 秒的问题并到 #67。
- **需要真机**：不需要。

**#52 [P2] 设备面板 › 本机：转回手机后如果 App Remote 连不上，只靠 10 秒一次的 watch 跟着**
- **用户会遇到**：在设备面板点本机，把音乐从音箱拉回来：如果手机上的 Spotify 没接住，或 App Remote 连不上（测试者的情况），Yoin 把手机显示为当前设备，最多 10 秒；命令提示"在本机打开 Spotify"；之后整个会话里歌词和下一首都会落后最多 10 秒。

**#54 [P2] 拔耳机或把 AirPods 放回盒子，会暂停音箱或电脑上的 Spotify**
- **用户会遇到**：Spotify 在 Connect 音箱或 Mac 上放，Yoin 在 iPhone 上开着看歌词。手机连着但没在用的 AirPods 放回盒子，或车载蓝牙断开：音箱暂停了，尽管手机的音频输出跟它毫无关系。手机的媒体服务重置也会暂停音箱。
- **原因**：任何"输出设备断开"的通知都会暂停引擎，不管是什么来源、在哪儿放（PlaybackSystem.swift:145-156），媒体服务重置也一样（163），最后给音箱发了 Web API 暂停（PE:230-238；SAO:1261-1275）。来电等打断结束后的恢复也不检查来源（PlaybackSystem.swift:181-183），"被打断而暂停"的标记也不会因为停止或接管而清掉。

- **修法**：输出变化和媒体服务重置时，只在 Yoin 自己的播放在放时才暂停（不是 Apple Music，也不是 Spotify）。当前来源变成外部、或当前没有歌时，清掉"被打断而暂停"的标记。

**#55 [P2] Yoin 在音箱或其他设备上驱动 Spotify 时，锁屏和控制中心没有控制（平台限制，只需写进文档）**

**#56 [P2] 停止、切账户或接管 Spotify 之后，Yoin 留着音频会话和锁屏控制，锁屏可能留一张空白的 Yoin 卡片**
- **用户会遇到**：先在 Yoin 放 Subsonic 的歌，再切到 Spotify 账户（或者 Yoin 发现音箱在放并跟上）：锁屏上可能一直有一个没标题、没封面的 Yoin 播放器。它的播放/暂停要么没用，要么悄悄控制 Spotify 所在的音箱。
- **原因**：移除锁屏控制、释放音频会话只在"准备出声"时做（PlaybackSystem.swift:92-101，由开始播放触发）。停止（PE:187-209；AppModel.swift:332-335）和接管（SAO:1449-1466 → AppleMusicAudioOutput.swift:303-309）都不经过那里，只清了卡片内容（PlaybackSystem.swift:307-316），播放/暂停的控制仍然注册着（200-211）。

- **需要真机**：空白卡片是否出现要真机确认；残留的锁屏控制从代码上是确定的。

**#57 [P2] Spotify 的时间会超过歌曲长度**

**#60 [P2] 在音箱上 Web API 开播进行中时，拖动或点歌词会丢**

- **原因**：全屏歌词只画歌词行（NowPlayingLyricsTools.swift:187-194）；第一句之前当前行是 -1（NowPlayingData.swift:38-41），定位函数直接返回（NowPlayingLyricsTools.swift:244）。
- **安卓怎么做**：LyricsFullscreenPane.kt:257-258、305-310、568-577。
- **修法**：在第一句之前加一行歌名/艺人（编号用 -1，不影响现有编号）。歌词有时间轴且还没到第一句时，它高亮并定位；不能选中；点它（有时间轴且不在选择模式时）跳到 0 并恢复跟随。
- **需要真机**：不需要。

**#63 [P2] 遥控音箱（或走 Web API）时，每 4 秒用一个稍旧的位置校准时钟：歌词略微落后，偶尔在两句交界处退回一下（打磨项）**
- **用户会遇到**：在音箱上放（或本机 App Remote 不通）时，高亮行整体比声音慢一个网络往返的时间，偶尔在交界处退回上一句一瞬间。
- **原因**：每 4 秒轮询，在响应到达时直接用它的位置作为当前位置（SAO:1543-1548、1754-1756），不补偿网络延迟。另一份审计里"每 4 秒明显跳回去"的说法已经被驳回；实际上是固定的小延迟加一点抖动。
- **安卓怎么做**：没有对应问题，安卓没有 Web API 轮询。
- **修法**：同一首歌在放、且没有刚暂停或继续时，位置加上实测往返时间的一半（或用响应自带的时间戳）；小于约 0.75–1 秒的修正忽略。换歌、播放状态变化或偏差大时照常校准。
- **需要真机**：需要。

**#64 [P2] iOS 没有"为你推荐"（Made For You：daylist、Discover Weekly、Release Radar、Daily Mix、On Repeat）**
- **用户会遇到**：安卓首页有"为你推荐"一栏，列出 Spotify 为用户生成的歌单，点开能看到歌。iOS 没有，Spotify 用户在 Yoin 里找不到这些歌单。
- **原因**：iOS 里没有相关代码；首页只读最近播放和收藏的专辑（SpotifySource.swift:61-84）。App Remote 的内容接口已经接好了（SR:451-460）。
- **安卓怎么做**：PR #239（main 2c54804a，0.6.1 已发布）：SpotifyMadeForYou.kt:1-211 经内容接口列出这一栏并排序；HomeMadeForYou.kt:39-148 按账户缓存，10 分钟后重读。
- **修法**：照搬：从内容接口读这一栏，取子项、排序，按账户缓存，10 分钟刷新。只在已经有 App Remote 连接时读（绝不为此唤醒，唤醒会开始放歌）；否则显示上次的缓存，没有缓存就隐藏这一栏。
- **需要真机**：需要。

**#65 [P2] 资料库 › 歌曲（喜欢的歌）和 › 艺人（已关注）在点喜欢或关注后不变**
- **用户会遇到**：在 Now Playing 点了喜欢，去资料库 › 歌曲：没有。在列表里取消喜欢：这一行还在（只是爱心空了）。在艺人页关注或取关：资料库 › 艺人不变。要下拉刷新或重启才更新。安卓里，喜欢的歌出现在最上面，取消的会淡出，关注也是即时增减。
- **原因**：点爱心后只更新了专辑页，并把 Subsonic 收藏标记为过期（LibraryStore.swift:128-136），从不更新"喜欢的歌"列表（964-980）。关注艺人对 Spotify 只记了一个覆盖值（1334-1350），艺人列表不动。歌曲列表不按爱心过滤（LibraryView.swift:587-603）。
- **安卓怎么做**：每次点爱心或关注后，从同步缓存重读喜欢的歌和已关注的艺人（LibraryViewModel.kt:1720-1800）。
- **修法**：在本地处理，不发网络请求：喜欢确认后把这首插到列表最上面，取消确认后移除，并存盘；关注/取关成功后在艺人列表里增删，并存盘。失败时不动（爱心本来就会弹回去）。
- **需要真机**：不需要。

**#66 [P2] 长时间运行时，Spotify 资料库、歌单页和首页从不刷新**
- **用户会遇到**：iOS 会把 Yoin 挂起好几天。在 Spotify App 里新建或编辑的歌单、新收藏的专辑、新关注的艺人、新喜欢的歌都不出现，要下拉刷新才有。打开过一次的歌单页一直显示旧的曲目，直到重启（它没有下拉刷新）。首页的 Spotify 部分一直是启动时的样子。
- **原因**：已经加载过的内容会被跳过（LibraryStore.swift:696-703），各个列表没有过期时间（846-980），歌单只要内存里有就不重新取（1198-1202）。首页加载过就直接返回（225-226；HomeView.swift:124-125）。只有 LibraryView.swift:185 支持下拉刷新。回到前台时只上传 scrobble（AppModel.swift:355）。
- **安卓怎么做**：同步设了 1 小时的有效期，先显示旧数据，后台再同步（SpotifyLibrarySyncCoordinator.kt:29、432；YoinRepository.kt:630-638）。
- **修法**：每项内容记下加载时间。回到前台、以及资料库或首页出现时，在后台重新加载超过 1 小时的内容，不清空现有的行。打开的歌单页，副本超过几分钟就在出现时重读。歌单页、专辑页、首页都加上下拉刷新。
- **需要真机**：不需要。

**#67 [P2] 被 Spotify 限流（429）后不记住：所有页面、轮询、watch 继续请求，可能拖长惩罚时间；提示是英文加原始秒数；遥控命令会被悄悄延迟**
- **用户会遇到**：Spotify 限流这个账号时（开发模式的 App 很常见，等待时间常常是几分钟到几小时），Yoin 照常请求：投屏或 App Remote 不通时 4 秒一次的 me/player 轮询、10 秒一次的 watch、每个资料库页面和每次搜索。页面显示英文"Spotify is rate limiting requests; try again in 3600s"。遥控音箱时，按一次暂停可能 15–30 秒都没反应，也没有任何反馈。
- **原因**：遇到 429 最多在 15 秒内重试两次，然后报错，但不记下要等多久（SpotifyWebAPI.swift:128-133），下一个请求照发。提示文字没有本地化（25）。轮询失败只记日志，定时器照跑（SAO:1538-1543、1593-1610）。播放命令也一样会睡过等待时间。
- **安卓怎么做**：每个账户一个限流开关，最长 24 小时；关着时在本地直接拒绝所有请求（SpotifyApiClient.kt:798-811、852-864）；关着时也跳过爱心检查（YoinRepository.kt:1869）。
- **修法**：在 SpotifyWebAPI 里给每个账户设一个开关：遇到任何 429，就关到"现在 + 要等的时间"（最多 24 小时），期间在本地直接报"被限流（还剩多久）"。开关关着时，轮询和 watch 跳过（App Remote 不受影响）。播放命令遇到 429 不等待，立即失败并提示。文案本地化，用相对时间（"约 1 小时"）。
- **需要真机**：不需要。

**#68 [P2] Spotify 搜索失败只给一个光秃秃的"重试"**
- **用户会遇到**：搜索失败（被限流、登录过期、离线）时只显示一个重试按钮。限流或登录已撤销时重试一样失败，用户不知道该等一会儿还是重新连接账号。安卓在按钮上方显示原因。
- **原因**：搜索失败时记了日志就把原因丢掉了（LibraryStore.swift:1305-1312）；搜索页的重试按钮没传原因（SearchView.swift:386-388），而这个按钮本来支持显示原因（LoadStates.swift:8-14）。
- **安卓怎么做**：LibraryScreen.kt:2469-2481 显示失败原因。
- **修法**：搜索失败时保存原因和诊断信息，传给重试按钮，跟资料库列表的做法一样。
- **需要真机**：不需要。

**#69 [P2] 每次会话第一次在"资料库"范围搜索，要等整个资料库重新下载一遍**
- **用户会遇到**：没打开过资料库时，第一次在资料库范围搜索会显示很多秒的骨架屏（资料库大的话：收藏专辑最多 40 页一页页地翻，再加艺人、歌单、6 页喜欢的歌），尽管磁盘上已经有一份。安卓立刻从本地数据出结果。
- **原因**：搜索前先等资料库和歌曲全部加载完（LibraryStore+SpotifySearch.swift:7-11）。加载时虽然先恢复了磁盘上的副本，但仍然要等网络请求完成（LibraryStore.swift:776-799）。专辑一页一页顺序翻，最多 2000 张（SpotifySource.swift:88-95）。
- **安卓怎么做**：直接搜本地数据库，不发请求（LibraryViewModel.kt:1874-1901）。
- **修法**：先用内存里或能从磁盘恢复的数据立即搜索并显示；后台开始加载，不等它。加载完如果还是同一次搜索，再重新搜一遍。
- **需要真机**：不需要。

**#70 [P2] 大的 Spotify 歌单加载慢，而且要么全有要么全无（最多 10000 首，一页一页取）**
- **用户会遇到**：第一次打开几千首的自建或协作歌单，要等所有页都到齐才显示。每次请求 50 首、按顺序来，2000 首要大约 40 次往返，再加大约 50 次一批批的喜欢状态查询。中途一次限流或网络抖动，整页失败，重试又从第 1 页开始。
- **原因**：一页一页顺序取，最多 10000 首，结束前什么都不显示（SpotifySource.swift:189-223）；之后还要等所有歌的喜欢状态查完（221；503-513）。除了 403 以外的任何错误都让整个加载失败（LibraryStore.swift:1198-1225）。
- **安卓怎么做**：页面读取最多 1000 首，其余页按位置 4 路同时取（SpotifyApiClient.kt:266-283、661-689、946）；完整的 10000 首只在备份时读；歌单页不显示爱心。
- **修法**：按总数用位置 3–4 路同时取剩下的页，第一页一到就显示。考虑限制在 1000 首（备份时保留 10000）。歌单页不查喜欢状态，或者显示之后再并行补上。后面的页失败时，保留已经读到的页。
- **需要真机**：不需要。

**#71 [P2] 用 ▾ 菜单"从资料库移除"的专辑，可能还留在资料库 › 专辑里**
- **用户会遇到**：移除专辑后，Yoin 立刻重读收藏列表，而 Spotify 那边的列表可能还带着它，于是它留着（或者又冒出来）在资料库 › 专辑里；首页"最近添加"也要等下次加载才更新。
- **原因**：写入后立刻强制重读专辑列表（AlbumLibraryMenu.swift:29-35），直接采用 Spotify 返回的列表，没有叠加本地的改动记录（SpotifySource.swift:88-95）。而且每次切换都要全部重读最多 40 页，有被限流的风险。
- **安卓怎么做**：读专辑列表时用"本地收藏改动记录"过滤（SpotifyMusicSource.kt:119-133）；收藏/取消时只记录改动，不重读（352-362）。
- **修法**：成功后直接在本地改专辑列表（移除，或插到最上面）。维护一份带检查点和 60 秒宽限期的收藏专辑改动记录，叠加到专辑列表和首页的结果上，代替立刻全部重读。
- **需要真机**：需要（Spotify 写入后多久生效）。

**#72 [P2] 专辑的"保存到/从资料库移除"状态在 Spotify 账户之间串了**
- **用户会遇到**：从一个 Spotify 账户切到另一个后，专辑 ▾ 菜单会短暂显示上一个账户的状态（只有另一个账户收藏的专辑，却显示"移除"）。新账户读取失败（被限流、离线）时，旧状态一直留着，点一下就执行了和预期相反的操作。
- **原因**：这个状态只按专辑 id 存，从来不清（AlbumLibraryMenu.swift:9-21）；切账户时的重置不清它（LibraryStore.swift:187-218）；读取时不检查账户有没有变，切换时用的是旧值（23-27）。
- **安卓怎么做**：状态按页面、按账户分开（YoinRepository.refreshFavoriteStates :1904-1905）。
- **修法**：切账户重置时清掉这些状态（或者按"账户 + 专辑 id"存）。读取过程中账户变了，就丢掉结果。
- **需要真机**：不需要。

**#73 [P2] 首页动态里，Spotify App 里的播放只显示成不带时间的"最近活跃"专辑（没有艺人，也没有单曲）**
- **用户会遇到**：主要在 Spotify 里听歌的用户，首页动态（最多 4 个位置）被 Spotify 最近播放的专辑填满，标签是"最近活跃"，没有时间，从不出现艺人和单曲。安卓用同一份最近播放生成带播放时间的专辑、艺人、单曲条目，还配艺人头像。
- **原因**：最近播放只被转成专辑，播放时间被丢掉（SpotifySource.swift:70-83；SpotifyDTOs.swift:97）；首页在不满 4 个时用它们补位，不带标签（LibraryStore.swift:535-544）。
- **安卓怎么做**：把 50 条播放记录转成带时间的专辑、艺人、单曲动态，并配头像（YoinRepository.kt:3616-3626、3651；HomeViewModel.kt:1198）。
- **修法**：把最近播放转成带时间的动态条目（专辑、艺人、单曲，按对象去重，从新到旧），和本地历史按时间合并，而不是在后面追加不带时间的专辑。和 #18 一起做效果最好。
- **需要真机**：不需要。

**#74 [P2] 网络差时，Spotify 请求可能卡 60 秒**
- **用户会遇到**：信号弱时，某个 Spotify 页面（或点爱心、改歌单）可能转圈长达一分钟才失败，一页一页翻的时候还会叠加。安卓 15 秒就放弃。
- **原因**：Spotify 的网络请求用的是系统默认的连接（SpotifyWebAPI.swift:58-61；AppModel.swift:988 没传自定义的），登录相关的请求也是（SpotifyAuth.swift:194、200-225）；默认超时是 60 秒。
- **安卓怎么做**：连接和读取超时都是 15 秒（SpotifyMusicSource.kt:929-933）。
- **修法**：SpotifyWebAPI 和 SpotifyAuth 共用一个专门的网络连接：请求超时约 15 秒，不等待网络恢复。可选：给翻页读取设一个总时长上限。
- **需要真机**：不需要。
