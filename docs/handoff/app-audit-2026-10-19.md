## 零、已知问题专项剖析：桌面 Widget 的取色为什么不是 Expressive 的？

通过排查 `widget/` 与 `ui/theme/`，桌面小组件（`PlayWidget` 与 `MemoryWidget`）颜色显得「灰暗、平淡、缺乏 MD3 Expressive 张力」并非单一原因，而是 **三处链路同时偏离了 App 本体的 Expressive 取色管线**：

### 1. `GlanceTheme` 默认回退到了系统 Tonal Spot，未接入 `DefaultColorScheme`（SPEC_2025 `SchemeExpressive`）
- **位置**：`widget/PlayWidget.kt:64`、`widget/MemoryWidget.kt:65`
- **现状**：两处均直接调用了无参的 `GlanceTheme { ... }`。在 `androidx.glance:glance-material3` 中，默认 `GlanceTheme.colors` 使用 `DynamicThemeColorProviders`，在 Android 12+ 上直接读取 `@android:color/system_accent1_*` 与 `system_neutral1_*` —— 即系统的 **Tonal Spot** 色板。
- **对比**：App 本体在 `ui/theme/DefaultColorScheme.kt:16-37`（2026-10-19 刚为解决「默认配色太平淡，三星刚登录时最明显」而改造）已弃用系统 `dynamic*ColorScheme()`，改用壁纸源色（近灰时回退 `YoinSeedArgb = 0xFF7B3FE4`）经 `ExpressiveColorSchemeFactory.fromSeed(..., SPEC_2025)` 生成 `SchemeExpressive`。
- **影响**：`PlayStrip`、`PlayStack`（底板 + 播放键）、`PlayShelf`（Hero + `secondaryContainer` 货架底）、`MemoryTimeline`、`WidgetEmpty` 读取的 `GlanceTheme.colors.widgetBackground` / `primary` / `secondaryContainer` 全部停留在灰暗的系统 Tonal Spot，与 App 内同源壁纸的 Expressive 配色完全脱节。
- **修复方案**：用 `ColorProviders(light = defaultColorScheme(context, dark = false), dark = defaultColorScheme(context, dark = true))` 传入 `GlanceTheme(colors = ...)`。

### 2. 封面取色 `WidgetArt.palette` 复用了 Memories 的暗墨色区间，而非首页 `ExpressiveBackdropPalette` 或 `SchemeExpressive`
- **位置**：`widget/WidgetArt.kt:67-85, 128-134`、`widget/PlayWidget.kt:155`
- **现状**：
  1. `WidgetArt.palette(bitmap)` 调用的是 `MemoryPalette.fromBackdrop(colors.seed, colors.accent)`，其中 `holdLightness(base, 0.22, 0.46)`（`ui/memories/showcase/MemoryPalette.kt:54-55, 67`）是为 Memories 浅色纸面上的**深色文字/按钮（ink）**设计的明度锁（L 锁在 `0.22..0.46`）。
  2. 当 `PlayStack`（2×2 堆叠小组件，`PlayWidget.kt:155`）把 `palettes[i].base` 直接涂在 `Bun` / `Ghostish` / `Circle` 异形底板上时，底板明度被压死在 `0.22..0.46`，远比首页 `HomeWidgetGrid` 使用的 `toneBackdropBase`（`ui/component/ExpressiveBackdropPalette.kt:315-320`，L 在 `0.24..0.62`）或 `ExpressiveColorSchemeFactory.fromSeed` 的 `primaryContainer` / `secondaryContainer` 暗沉。
  3. 当封面只有棕褐/黑白像素导致 `CoverSeedExtractor.seedSwatch` 返回 `null` 时，`ExpressiveBackdropPalette.kt:265-274` 有 12 色 `clearFilters()` 兜底，而 `WidgetArt.palette` 直接退回写死的暗紫灰 `WidgetPalette.Fallback`（`0xFF6B5B95`）。
  4. 当封面图片加载失败为 `null` 时，`PlayStrip` / `PlayStack` / `PlayShelf` 传入了 `android.graphics.Color.GRAY`（`0xFF888888` 纯死灰，`PlayWidget.kt:99, 156, 188`）。

### 3. `PlayStrip` / `PlayShelf` 算出了封面调色板却完全丢弃不用，且 `MemoryStrip` 深色模式对比度存在 Bug
- **位置**：`widget/PlayWidget.kt:62, 84, 86`、`widget/MemoryWidget.kt:100, 131-135`
- **现状**：
  1. `PlayWidget.provideGlance`（第 62 行）对 6 张封面全部计算了 `palettes`，但 `PlayStrip`（1×N 条形）与 `PlayShelf`（宽屏双段）连 `palettes` 参数都没接收，左侧 `Bun` 异形头、右侧大播放键、下层货架全部用系统色，完全没有「封面驱动 Expressive 配色」的呼应。
  2. **`MemoryStrip` 深色模式 Bug**：`MemoryWidget.kt:100` 写了 `val accentInk = dayNight(palette.base, palette.base)`（白天黑夜都传了 `palette.base`！）。在深色模式下，`bgDark` 是 `deep` 向黑色混合 38%（极暗），而 `palette.base` 明度仅 `0.22..0.46`，导致 28sp 的大号评分数字和 `lastHeard` 在深色背景下暗成一团（对比 `HomeWidgetGrid.kt:710-714` 在深色下明确改用 `accentColor`）。

## 一、方向 1：稳定性审查（动画破绽或不连贯、性能、Bug）

### 1.1 动画破绽与转场不连贯

#### [A-1] 从桌面 Widget 点击进入详情页，破坏了 Wide 同窗分列原则与底栏预测性返回手势（高优）
- **位置**：`widget/WidgetRefresher.kt:98-110`（`WidgetLaunch.handle`）、`widget/WidgetPlayActivity.kt:33, 39`
- **现象与根因**：
  1. `WidgetLaunch.handle` 处理 `ACTION_OPEN_DETAIL` 时，直接构造 `AlbumDetailActivity` / `PlaylistDetailActivity` / `ArtistDetailActivity` Intent 并调用裸 `activity.startActivity(target)`。
  2. **破绽一（窄屏/中屏返回底栏硬切）**：未走 `launchDetailFromShell`，Intent 上缺少 `DETAIL_EXTRA_FROM_SHELL`、`DETAIL_EXTRA_BAR_HANDOFF`、`DETAIL_EXTRA_BAR_MORPH`、`DETAIL_EXTRA_HANDOFF_GENERATION` 与 `DETAIL_EXTRA_BENEATH_WINDOW`。导致进入时没有底栏 morph 交接，且从详情页侧滑返回时 `morphBarOnBack = false`、`bridgeBackToShell = false`，底栏固定在 `[Play ▾]` 姿态不动，直到 Activity 销毁瞬间硬切成首页底栏，且被覆盖的 Shell 窗口动画门控无法通过 `beneathWindow` 提前唤醒。
  3. **破绽二（大屏/平板横屏违背架构铁律）**：在 Wide 窗口（如 Pixel Tablet 横屏，`hasDetailPane == true`）下，按照 `docs/adaptive-principles.md` 原则 3，详情必须在 Shell 右列打开，绝不启动独立详情 Activity。但 Widget 点击在平板横屏下依然强行拉起了全屏详情 Activity。

#### [A-2] 歌单详情页删除歌单时直接 `finish()`，跳过返回收尾编排导致 Shell 残留在 `-96dp`（中优）
- **位置**：`ui/detail/PlaylistDetailActivity.kt:123-125`
- **现象与根因**：
  - `viewModel.deleted.collect { finish() }` 直接调用了 `finish()`，既没有调用 `endShellHandoff()`，也没有走 `backCollapse.requestBack()`。
  - 当从 Compact 首页进入歌单并删除时，Shell 底层内容此时停留在 `-96dp` 的 receding 位姿且底栏处于 detail split 形态；直接 `finish()` 会导致在 220ms 窗口淡出期间 Shell 仍卡在 `-96dp`，直到 `onStop()` 触发 `publishShellHandoffSettled()` 才滞后跳回原位。
  - **建议**：改为调用与顶部返回键一致的退场编排（或先 `endShellHandoff()` + 触发 `backCollapse.requestBack()`）。

#### [A-3] Now Playing 下拉/预测性返回关闭时的视觉破绽：遮罩不随进度淡出、顶边 0dp 直角硬切、像素魔法数未转 dp（中优）
- **位置**：`ui/nowplaying/NowPlayingOverlayHost.kt:194-195, 225-229, 388-399, 502-556, 612-615`
- **现象与根因**：
  1. **遮罩未耦合手势进度**：`scrimAlpha`（第 388 行）只监听布尔值 `expanded && !panelMode`。当用户在手机全屏或放大态向下拖拽关闭 NP（或侧滑预测返回触发 `closeBackLevel`）时，播放器向下滑开露出背后的首页，但上半屏的 50% 黑色遮罩纹丝不动，直到松手 `expanded = false` 才开始淡出（违背 `AGENTS.md`「Shared element, scrim, and shell feedback should stay in the same progress family」）。
  2. **下滑时顶边为 0dp 锐利直角**：`!panelMode` 下播放器容器下拉进入屏幕中部时，没有像 `Memories`（`memoriesDismissCorners`）或 `DetailPredictiveBackCollapse`（`PopPageCornerRadius`）那样随进度加上 28dp 顶部圆角，在圆角手机屏上拉出一道横贯屏幕的 0dp 直角硬边。
  3. **裸像素常量未按屏幕密度折算 dp**：`predictiveBackProgress * 1200f`（第 226 行）、`dismissDragPx > 240f || velocity > 800f`（第 542 行）、`dismissDragPx / 240f`（第 613 行）全部是裸 px 常量。在 3.5x 密度的手机上 `240px` 仅约 `68dp`，而在 2.0x 的 Pixel Tablet 上则是 `120dp`，不同设备上手感阈值相差近一倍。

#### [A-4] 歌词选择模式与首页就地编辑模式的系统返回缺少预测性手势预览（低–中优）
- **位置**：`ui/nowplaying/LyricsSelection.kt:420`、`ui/navigation/YoinNavHost.kt:1279`
- **现象与根因**：
  - 歌词选择模式（`✓`）和首页编辑模式（`HomeSurface.Edit`）均使用普通 `BackHandler` 而非 `PredictiveBackHandler`。手指从屏幕边缘内滑时画面完全静止，没有任何跟手缩放或工具条淡出反馈（对比 `Memories` 的 `TitleEdit` 已接入 1:1 淡出预览）。

#### [A-5] 多处 BottomSheet 仍使用裸 `ModalBottomSheet` 而非 `YoinModalBottomSheet`（低优）
- **位置**：`ui/component/QueueSheet.kt:178`、`ui/component/DevicesSheet.kt:75`、`ui/component/AddToPlaylistSheet.kt:103`、`ui/nowplaying/LyricsShareCard.kt:309`、`ui/settings/SettingsScreen.kt:1123`
- **现象与根因**：`predictive-back` Invariant 15 规定组件应统一使用 `YoinModalBottomSheet`（内建 `SheetWindowBack` 桥接，防止在提供自定义 `LocalNavigationEventDispatcherOwner` 的子树中丢失系统返回）。目前这 5 处仍残留原生 `ModalBottomSheet`；此外在 Wide 详情列（`DetailPaneHost`）中打开 `PlaylistDetailScreen` 的重命名/删除 `AlertDialog`（`PlaylistDetailScreen.kt:358, 495`）同样运行在 `paneBackOwner` 子树中，建议真机核验 Dialog 窗口级返回。

### 1.2 性能与死代码/假状态隐患

#### [P-1] `AudioVisualizerManager` 全仓从未启动，但 6 个核心页面仍在持续订阅并传递恒为 0 的 `playbackSignal`（中优）
- **位置**：`player/AudioVisualizerData.kt:69`、`player/PlaybackService.kt:99, 141`、`AppContainer.kt:447`、`ui/navigation/YoinNavHost.kt:403`、`ui/detail/AlbumDetailActivity.kt:95`、`ui/detail/ArtistDetailActivity.kt:84`、`ui/detail/PlaylistDetailActivity.kt:99`、`ui/nowplaying/NowPlayingOverlayHost.kt:466`
- **根因**：`PlaybackService` 虽然把 `player.audioSessionId` 写进了 `PlaybackService.audioSessionId`，但全仓**没有任何地方调用 `audioVisualizerManager.start(audioSessionId)`**（`docs/design.md:590` 亦有提及）。
- **影响**：
  1. `ExpressivePageBackground` 中的 `playbackSignal * 0.03f` 呼吸加成、`NowPlayingScreen` 的 `hasAudioSpectrum` 永远为 `0f` / `false`。
  2. 若短期内不打算接通 `Visualizer`（且 `Visualizer` 需要 `RECORD_AUDIO` 权限，否则必然抛异常走 `startSimulation()` 30Hz 协程空转），应当清理掉各 Activity / Composable 中冗余的 Flow 订阅；若打算启用「播放时微妙律动」，则直接用纯数学相位或接通无需录音权限的播放态信号，避免 `startSimulation()` 在后台 33ms 一帧空跑。

#### [P-2] `LibraryScreen` 中歌曲列表的「正在播放」状态完全失效（Bug / 假参数）
- **位置**：`ui/library/LibraryScreen.kt:1827-1828`、`ui/component/SongListItem.kt:51-52, 96-112, 129-136`、`ui/component/ExpressiveBackdrop.kt:34-35`
- **根因**：
  - `LibraryScreen` 在歌曲 Tab、收藏 Tab、搜索结果中都向 `SongListItem` 传入了 `isNowPlaying = isPlaying && song.id.toString() == activeSongId`。
  - 但 `SongListItem` 既没有在 `isNowPlaying == true` 时把标题染成 `MaterialTheme.colorScheme.primary`，也没有渲染跳动的均衡器图标 `rememberEqualizerSymbolPainter()`，而是把 `isNowPlaying` 传给了 `ExpressiveBackdropArtwork` 的 `isPlaybackActive` 参数。
  - 而在 `ExpressiveBackdrop.kt:34-35` 中，`@Suppress("UNUSED_PARAMETER") isPlaybackActive: Boolean = false` 被直接忽略了！
- **结果**：用户在 Library（歌曲、收藏、搜索结果）中点击播放任何歌曲时，列表中当前播放的那一行**没有任何视觉高亮或动态均衡器指示**。

#### [P-3] `NowPlayingOverlayHost` 手势状态使用了装箱 `mutableStateOf(0f)`
- **位置**：`ui/nowplaying/NowPlayingOverlayHost.kt:194-195`
- **根因**：`dismissDragPx` 与 `predictiveBackProgress` 在 60/120Hz 手势回调中逐帧写入，使用了 `mutableStateOf(0f)` 而非 `mutableFloatStateOf(0f)`，每帧产生不必要的 Float 装箱分配。

## 二、方向 2：功能完整度审查（可攻克的常用功能优先）

按「后端/数据层已具备或极易攻克、对日常听歌体验提升最大」排列优先级：

### 优先级 P0：数据层/ViewModel 已写好，仅差 UI 临门一脚的「半成品」缺口

#### [F-1] 歌单详情页（Playlist Detail）功能严重滞后于专辑页（高价值、极易攻克）
对比 2026-10-05 ~ 10-17 打磨完善的 `AlbumDetailScreen`，`PlaylistDetailScreen`（含 `PlaylistDetailActivity` 与 `PlaylistPaneEntry`）存在四处明显断层：
1. **无法从歌单中移除单曲（后端 + VM 均已实现，唯独 UI 没接！）**
   - `PlaylistDetailViewModel.removeTrack(position, trackId)`（`ui/detail/PlaylistDetailViewModel.kt:176-196`）以及 Subsonic / Spotify 的 `removeTracksFromPlaylist` 早已完整实现，连 `PlaylistSong.position` 和错误文案 `detail_playlist_error_remove` 都已就绪，但 `PlaylistDetailScreen` 完全没有调用 `removeTrack` 的入口！
2. **歌单曲目行不支持长按弹出 `TrackMenuSheet`**
   - 专辑页和 Now Playing 封面长按都能呼出统一的 `TrackMenuSheet`（下一首播放、加入队列、加入歌单、前往专辑、在剪贴簿里查看、前往艺术家、分享、在外部应用中打开），唯独歌单里的曲目行（`PlaylistTrackRow`，`PlaylistDetailScreen.kt:1047`）只有单击播放，长按毫无反应。将 `TrackMenuHost` 接入歌单页，并在 `canWrite == true` 时附带「从本歌单移除」，即可一举补齐。
3. **歌单底栏 `Play ▾` 菜单缺失「下一首播放 / 加入队列 / 加入歌单 / 在 Spotify 或 Apple Music 中打开」**
   - `AlbumDetailActivity` 和 `ArtistDetailActivity` 都接入了 `rememberDetailMenu`（`ui/detail/DetailMenu.kt`），而 `PlaylistDetailActivity` 和 `PlaylistPaneEntry` 没有接入 `rememberDetailMenu`，导致歌单页点 `▾` 只有 Shuffle play，不能把歌单「加入队列」或「下一首播放」。
4. **歌单分享丢失了公开链接（`webUrl`），且曲目行缺少当前播放高亮与不可播徽标**
   - `MusicSource.kt:178` 已经实现了 `WebLinkKind.Playlist`，但 `PlaylistDetailActivity.kt:227-236` 与 `PlaylistPaneEntry:383-386` 分享时只发了纯文本歌单名，没调 `rememberDetailWebLink(app.container, WebLinkKind.Playlist, playlistId)`。
   - `PlaylistTrackRow` 缺少 `currentTrackId` 播放中指示（跳动均衡器 + 主色标题）及 Apple Music 不可播曲目的 `UnavailableTrackBadge`。

#### [F-2] Library（歌曲 / 收藏 / 搜索结果）与歌手页「常听曲目」未统一接入 `TrackMenuSheet`
- **位置**：`ui/library/LibraryScreen.kt:1826`、`ui/detail/ArtistDetailScreen.kt`
- **现状**：
  - 在 Library 的歌曲列表、收藏列表和搜索结果中，长按一首歌目前只触发 `onAddSongToPlaylist`（直接弹 `AddToPlaylistSheet`）；而在不支持写歌单的 Apple Music 账号下，`onAddSongToPlaylist` 为 `null`，长按歌曲**完全无反应**。
  - 在歌手详情页的「Most Played」曲目列表中，长按歌曲同样没有任何菜单。
- **可攻克方案**：将 `TrackMenuSheet` 推广为全 App 所有单曲行的标准长按面板（在 Library / 搜索 / 歌手页中长按单曲即可：下一首播放、加入队列、加入歌单、前往专辑、前往歌手、查看剪贴簿、分享）。

### 优先级 P1：高频日常听歌刚需（无额外后端依赖，纯客户端可独立攻克）

#### [F-3] 睡眠定时器（Sleep Timer）—— 音乐 App 最高频的日常刚需之一
- **现状**：全仓搜索无任何 Sleep Timer 实现。到了夜晚听专辑或环境音乐时，用户没有「15 / 30 / 45 / 60 分钟后暂停」或「播完当前歌曲/当前专辑后暂停」的能力。
- **切入位置**：天然适合放在 Now Playing 封面长按菜单的第三组（与现有的「屏幕常亮」开关并列，见 `docs/design.md:198`），并在开启时于 Now Playing 顶栏或胶囊旁展示轻量倒计时胶囊，到点时通过 Effects/Volume 渐弱平滑暂停 `PlaybackManager`。

#### [F-4] 专辑页（Album Detail）在 Subsonic 下缺少「收藏/星标整张专辑」入口
- **位置**：`ui/detail/AlbumDetailScreen.kt`、`ui/detail/DetailMenu.kt`、`data/source/subsonic/SubsonicMusicSource.kt`
- **现状**：
  - Spotify 在专辑页 `▾` 菜单中有「保存到资料库 / 移出资料库」（`Capability.ALBUM_SAVE`）。
  - Subsonic 虽然在 `Library` 有「收藏（Favorites）」Tab 且 `getStarred2` 会展示星标专辑，但在 `AlbumDetailScreen` 上只能给单曲点心形星标，**没有任何按钮或菜单项可以星标/取消星标整张专辑**（`SubsonicApi` 的 `star(albumId = ...)` 支持对专辑星标）。
- **可攻克方案**：在 Subsonic 下为专辑页提供专辑级收藏/星标开关（或复用 `▾` 菜单的收藏行）。

## 三、方向 3：易理解度与惊艳程度审查（UX 可发现性 & Wow Factor）

### 3.1 易理解度与可发现性（Discoverability）痛点

#### [U-1] 核心杀手锏手势藏得较深，首次触发缺乏轻量微交互线索
Yoin 拥有大量极具巧思的交互，但多个入口属于「知道了很爽、不知道永远找不到」的隐式手势：
1. **播放模式按钮「长按分裂为双段胶囊」**（`ui/nowplaying/PlaybackControls.kt:PlayModeButton`）：
   - 单击按格雷码顺序在 4 种模式间轮转，长按分裂成「左随机 | 右循环」双段胶囊。虽然 `HomeBubbleTip` 里有一条提示，但在 Now Playing 现场，用户连续快速点击播放模式键 2–3 次时，往往是因为想单独切某一条轴——此时若能自动触发一次轻量的「分裂展开提示」或微弹性呼吸，可发现性会提升数倍。
2. **专辑详情页第 2 页「拼贴手册（Scrapbook）」**：
   - 专辑页顶栏右侧虽然有页点（Page indicator dots），但第 1 页主体是上下拉动的曲目表，很多用户不会意识到专辑页还能**横向左滑**进入极具惊艳感的第 2 页拼贴手账（Scrapbook）。当用户在专辑页刚写完乐评、打完分，或者该专辑已有笔记时，顶栏第 2 个页点可以做一次轻量脉冲/色彩呼吸，引导用户横滑发现手账页。
3. **首页下拉进入 Memories 与长按底栏 Library 直接搜索目录**：
   - 首页顶部的下拉箭头在滚动后淡出，新用户如果不等 4–5 秒看气泡闲聊，很容易把 Memories 当成只能点气泡进入的页面。

#### [U-2] 专辑笔记（Album Note）在 Scrapbook 与 Memories 中「只读不可写」的困惑
- **位置**：`docs/design.md:427`、`data/local/AlbumNote.kt`、`ui/detail/AlbumScrapbookPage.kt`
- **现状**：`album_notes` 是旧表，目前在 Scrapbook（折角便签）和 Memories 日记（6dp 空心小珠）中仍然会渲染历史数据，但全 App 已经没有任何入口可以新建、编辑或删除它。如果老用户或迁移用户看到折角便签想点开修改，却发现它是纯只读的，而旁边只有「乐评（Review）」可写，容易产生困惑。建议允许点击已有专辑笔记便签进行编辑/转化为乐评或删除。

### 3.2 惊艳程度（Wow Factor）再拔高机会

1. **桌面 Widget 全面升级为 SPEC_2025 Expressive + 封面色调联动（立竿见影）**
   - 修复第零节的三个问题后：
     - `GlanceTheme` 接入 `defaultColorScheme`（`SchemeExpressive` SPEC_2025）；
     - `PlayStack` 的 `Bun` / `Ghostish` / `Circle` 异形底板改用 `ExpressiveBackdropPalette` 的明亮色调或 `ExpressiveColorSchemeFactory.fromSeed` 的 `primaryContainer` / `tertiaryContainer`；
     - `PlayStrip` 的 `Bun` 头与播放键、`PlayShelf` 的 Hero 段接入第一张封面的 `SchemeExpressive` 配色；
     - `MemoryStrip` 深色模式下的评分大字改用高明度 `accent` / `liftHue`。
   - 桌面小组件将瞬间拥有与 App 内部一致的鲜明 Expressive 视觉张力。

2. **真实或节拍驱动的微妙背景呼吸（修复 `AudioVisualizerManager` 断路）**
   - 当前 `ExpressivePageBackground` 和 `NowPlayingScreen` 的音频可视化响应因 `AudioVisualizerManager` 未调用 `start()` 而完全静默。接通安全的播放态呼吸驱动（或在本地 ExoPlayer 播放时在已授权/无权限兜底路径下驱动柔和的包络），能让「背景随音乐呼吸」这一设计文档承诺的亮点真正落地。

3. **Now Playing 下拉关闭的「圆角 + 遮罩同源跟手」打磨**
   - 为 `NowPlayingOverlayHost` 补上随 `dismissFraction` 实时渐变的顶部 28dp 圆角与遮罩透明度衰减，让全屏播放器的下拉/返回手势与 `Memories`、详情页的 AOSP 预测性返回达到完全同级的物理细腻度。
