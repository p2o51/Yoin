# 溶解式设计（Dissolve）交接：给 Claude CoWork

> 2026-09-30，由 Claude Code 写。目的：和用户一起把“溶解”细化成一条通用设计原则，并扩展到底部浮动栏和顶部状态栏。
> 本仓库的 `docs/design.md` 是 UI 决策的最终来源；这里是背景、现状和待讨论问题。用户用中文交流。

---

## 1. 这条原则是什么（已被用户认可的部分）

**滚动内容撞上固定 chrome 的交界处，不往交界上盖任何东西，而是把遮罩做进每个 item 里：图形溶解，文字淡出。**

- **图形**（封面、头像、缩略图）滑向交界时碎成错列波点。点阵锚定在图形自己身上，跟着它走；越靠近交界点越小，到交界线正好消失。点的颜色就是图形自己的像素，不取色、不染色。
- **文字**只按屏幕位置渐隐，不拆成点（小字拆点后既难读又脏）。
- **动效**：溶解程度只由位置决定。停止滚动后有约 0.5 秒的“余韵”（点沿流向再漂一小段然后停住），静止时完全不动。
- 用户原话：“完美解决了 progressive blur 和 Material Design 3 之间的一些冲突”，并且希望它成为可复用的通用语言，甚至用到其他项目。

它和切歌时的封面波点溶解（`ArtworkHalftone`，Codex 做的，用户和 Codex 一起讨论出来）是同一套视觉：同样约 6dp 的错列网点、同样的流场。

## 2. 走过的弯路（不要再提）

用户在原型里比较过 8 种“盖在交界上”的方案，全部否掉：

| 方案 | 结论 |
| --- | --- |
| A 硬截断（原状） | 难看，这是问题本身 |
| B 透明度渐隐 | 普通 Android 做法，太平 |
| C 渐进模糊 | iOS 做法，和 MD3 气质冲突 |
| D/E/F 整片内容碎成点 | 文字碎成点很脏，像“坏掉”而不是过渡 |
| G 顶部底色以网点渗下来 | 克制但无趣 |
| H 参考 Gemini 的光晕网屏（按下方内容取色） | 最接近但被否：太高；看起来像一条黑带、没有衔接；取色后发现上沿必须保持背景色 |

用户随后提出“反过来，把遮罩做在每个 item 内部”，这就是现在的方案。另外否掉了“静止时常驻微弱动态”（理由：过渡带几乎一直有内容、处在阅读区、耗电），改为只在停下后有余韵。

原型实验页（claude.ai 私有 artifact，可能打不开）：https://claude.ai/artifact/94SonnytwCPaiUatm3ZYVw ——其中的 I 方案是这个原则的最初形态，但数值已经过时。

## 3. 现在的实现

**文件**：`app/src/main/java/com/gpo/yoin/ui/component/SeamDissolve.kt`（尚未提交，见第 6 节）

- `Modifier.seamDissolveViewport { state.seamScrolledPx() }`：挂在滚动容器上，交界 = 这个容器的上沿。它同时通过嵌套滚动拿到滚动增量，驱动余韵。
- `Modifier.seamDissolve()`：给图形。API 33+ 用 AGSL `RuntimeShader` 作为 `RenderEffect`；更低版本用 Path 拼点 + `clipPath` 兜底（两者已截图对比过，形态一致）。
- `Modifier.seamFade()`：给文字，`saveLayer` + `BlendMode.DstIn` 竖向渐变。
- 后两者不在 viewport 内时是空操作，所以已常驻挂在共享组件上（`AlbumCard`、`SongListItem`）。只有进入过渡带的 item 会重绘。
- 已接入：Library 的 Artists / Albums / Songs / Playlists / Favorites 五个标签。

**数值**（`SeamDissolveTokens` 和 `YoinMotion.SeamFlowSettleStiffness`）：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| Band | 36dp | 过渡带高度 |
| SolidFrom | 1.34 × Band ≈ 48dp | 离交界这么远以下，图形是完整实色 |
| RevealDistance | 40dp | 滚动前 40dp 内，过渡带从 0 长到满；静止在顶部时不出现 |
| Pitch | 6dp | 网点间距，同切歌溶解 |
| TextFadeFraction | 0.8 | 文字在 0.8 × Band ≈ 29dp 处开始变淡 |
| FlowLag | 0.5 × Band | 余韵最大落后量 |
| SeamFlowSettleStiffness | 90（ω = √90） | 余韵衰减速率，约 0.5 秒停稳，不回弹 |
| Library 胶囊下固定间距 | 4dp（原 14dp） | 用户要求压缩：“做这个动画就是为了节约这个距离” |
| 网格顶部内边距 | 8dp（原 12dp） | 静止时封面离胶囊 12dp（原 26dp） |

**余韵模型**：网点的流动相位由一个一阶跟随者驱动（帧时钟积分），落后内容的量 ∝ 滚动速度，封顶半个过渡带；内容停下后以停前速度继续漂，指数衰减到 0。跟随循环是唯一的负责人，中途交接给 `Animatable` 会在停下时产生 2 帧顿挫（踩过的坑）。

**相关文档**：`docs/design.md` 的 Library 小节和“关键转场动画”表里有 “Library 列表滚到筛选胶囊下” 一行。

## 4. 用户最新反馈：安全距离太多

> “开始溶解的时候给的安全距离太多了，感觉美观或者说效果有点高于实用性了。”

按现在的数值，内容**离交界还很远就开始受损**：

- **图形**：网点之间出现缝隙大约从交界下方 31dp 开始（前沿起伏会让它在约 23–39dp 之间浮动），到约 7dp 处网点小到看不见；48dp 以下才完全是实色。
- **文字**：从 29dp 开始变淡，到 7dp 时只剩约 6% 的不透明度。
- 对照：一个专辑卡片是 118dp 的封面加约 40dp 的文字，也就是说大约 1/5 到 1/3 张卡片的高度处在“看不清”的状态。

可以讨论的方向（都还没定）：

- 过渡带整体再缩短（比如 16–24dp）。
- 改曲线：内容保持完整直到离交界很近，最后十几 dp 才快速碎掉（现在的网点半径几乎随距离线性变化）。
- 把过渡带和“本来就空着或被遮住的空间”挂钩，而不是一个独立的数值。原则可以写成：**溶解只能占用原本就不可读的空间，不能吃掉可读内容。**
- 文字的淡出区间单独再缩短。

## 5. 想和你讨论的两个扩展

### 5.1 底部：让溶解把 Now Playing 浮动栏后面的内容也处理掉

- **现状**：内容滚到底部浮动栏（Now Playing 胶囊 + Home/Library 导航，悬浮、左右有边距）下面时直接从栏后穿过，靠栏的阴影分层。列表底部留了 108dp 加导航条高度的内边距。
- **难点**：
  - 交界不再是一条水平线。栏是悬浮的胶囊，栏的左右两侧和下方都还能看到内容。交界应该是一条水平线、跟着胶囊轮廓走（到胶囊边缘的距离场），还是别的形状？
  - 现在的着色器假设“内容向上移动撞上顶部交界”，需要推广到方向朝下，甚至任意形状。
  - 浮动栏在主页和各个详情 Activity 之间要像素级对齐，并且有一整套阴影交接逻辑（`BottomBarShadow.kt`）。溶解如果取代阴影作为分层手段，要考虑跨窗口的情况。胶囊本身还会展开成全屏的 Now Playing。

### 5.2 顶部：Home 标题和状态栏

- **现状**：Home 的大标题（`HomeEditorialContent.kt` 里的 `HomeContentHeader`，`headlineLarge`）是列表第一项，会跟着滚走；之后内容直接滑进状态栏下面，没有任何保护，会影响状态栏图标的可读性。Library 的顶部是固定的，没有这个问题。
- **用户的想法**：“上面的颜色会通过波点过渡流进状态栏”，但要非常顺滑，用户自己也觉得这个设计很难想清楚。
- **可以讨论的点**：
  - 内容在碰到状态栏下沿前溶解干净，让状态栏始终落在干净的背景上，从而保证图标对比度（现在状态栏图标深浅由 `SystemBarStyle.auto` 决定）。
  - 反方向：页面顶部的颜色（`ExpressivePageBackground` 的渐变）以网点的形式向下流、形成一层“网点状态栏保护”，密度越往上越高。
  - 大标题本身怎么退场：它是大号展示字体，算“图形”可以溶解，还是按“文字”规则只淡出？这关系到原则里“图形/文字”怎么划分。

## 6. 需要一起定下来的原则问题

1. **适用边界**：什么样的交界用溶解，什么时候用淡出或什么都不做。
2. **图形和文字怎么分**：封面、头像、缩略图算图形；图标、筛选胶囊、带底色的卡片、大标题分别算什么？
3. **交界的几何**：水平线、跟着 chrome 形状走、还是多个交界。点阵锚定在内容上（现状）而不是屏幕上。
4. **尺寸规则**：实用性优先。过渡带高度怎么由“空着或被遮住的空间”推导出来。
5. **颜色**：网点永远用内容自己的像素，不染色、不加光晕（H 方案的教训）；交界的上沿必须保持背景色。
6. **动效**：只随位置和余韵变化，没有常驻动画；省电模式和系统“移除动画”下关闭余韵。
7. **性能**：只有进入过渡带的元素付出代价；静止时零开销。真机（Pixel）上还没实测，模拟器的帧数据没有参考价值。

## 7. 工作上的约定

- **所有改动都还没提交**，全部堆在 `codex/provider-capability-ui` 的工作区里（这个分支的 HEAD 和 main 相同）。用户明确要求**等全部做完再统一拆分和提交**，不要自己拆分、提交或切换分支。本地快照在 `wip/backup-2026-09-29`。
- 项目规定弹簧和动效参数都在 `ui/theme/Motion.kt` 的 `YoinMotion` 里定义；`MotionGuardrailTest` 禁止在 `ui/` 下直接写 `spring(`、`fadeIn(` 等。
- 做可视化验证时，别用“逐步截屏再拼成视频”的办法：它会压缩时间，跑马灯之类按时间走的动画看起来会乱抖（踩过的坑）。用 `app/src/androidTest/java/com/gpo/yoin/ui/library/LibrarySeamPreviewTest.kt`（`-e captureLibrarySeam true`），它用暂停的测试时钟逐帧推进，输出 60fps 真实时间的帧序列。
- 模拟器 `emulator-5554` 同时被其他会话使用（上面还有别的应用），不要改它的全局设置。
